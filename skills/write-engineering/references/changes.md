# 保存變更當時的理由

優先遵循目標 repository 的語言、commit、PR 與貢獻規則，不把個人的格式偏好套到所有專案。

Commit 或 PR 描述應讓未參與對話的維護者理解：

- 哪個情境觸發了什麼問題，以及對使用者或系統的影響。
- 為何選這個修改；若有實際衡量的取捨或限制，就交代它。
- 現在的行為與支持它的驗證。沒有執行的檢查不可寫成成功。

深度依變更大小調整，不要求每筆 commit 填固定小節。避免只列「修改哪些檔案」，也不要把整段聊天或所有曾放棄的方案搬進歷史。相依的必要脈絡要留在描述裡，連結作補充。

例如，假設程式與重現已支持以下理由：

> 在批次工作入列前檢查可用容量
>
> 原先逐筆入列，第二筆遇到容量上限時會回報失敗，但第一筆已留在佇列。呼叫端收到失敗時，無法判斷哪些工作其實已被接納。
>
> 改為先驗證整批輸入與容量，再一次入列，讓拒絕的請求保留原有狀態。以容量不足與重複識別碼的案例驗證拒絕路徑。

這是說明結構的假設範例，不能直接拿去描述尚未驗證的真實變更。Kernel 等專案的 `Fixes`、`Link`、`Signed-off-by` 和 patch 系列規則，依當前官方及子系統文件處理，不編造標籤或他人身分。
