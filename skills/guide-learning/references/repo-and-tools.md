# Repo 與新工具的帶讀入口

## 陌生 repo

先確定要理解的行為，而非承諾讀完整個 repository。

1. 從專案說明、實際 build/run 入口、測試及相關模組建立位置感。
2. 選一個可觸發的操作，先觀察輸入與結果，再追蹤入口、guard、狀態與資源生命週期。
3. 沿來源說明設計與限制。同步 call、queue、callback 與裝置通知分開畫；推測不能偽裝成執行紀錄。
4. 依學習目的安排一個小變化：改輸入、預測分支、補觀測或修正重現出的缺陷。寫入前仍遵循當次授權。

Linux kernel 或 Boost 等大型專案先固定版本、子系統／library、組態和一個問題。準備貢獻時才查當前專案與該元件的官方流程，不將 Linux 郵件流程或某個 Boost library 的要求當成通則。交付與外部操作依專案規則列出的 delivery 指引。

希望邊學邊貢獻時，選一個能在現有環境重現和驗證的小問題，先讀附近測試、歷史改動及維護者要求，再解釋最小 patch 為何足夠。收到 review 時，區分誤解、需要補的證據與設計取捨；修訂後重驗相關行為。不要替使用者承諾未做的測試，也不把代寫 patch 當成他已理解；想練習時可邀請他預測一個相近案例，再用來源或實驗核對。

FreeRTOS／STM32 的教材需對應實際晶片、board、port、工具鏈與韌體版本。不把模擬器、host 測試、成功 build 或 flash verify 當成板上行為已驗證；操作實板前先確認當次權限。

數值研究或股票分析程式可從一筆資料的來源、時間戳、轉換到結果追蹤；原始資料、計算結果與採用建議分開。可重跑的程式不會自動證明模型、投資結論或實際獲利。

## 新工具

先講使用者目前的工作為何需要它，再帶完一個最小任務。交代執行位置、必要輸入、命令、預期結果與常見失敗入口；不要預先灌入完整功能表。

安裝、修改系統設定、啟動 daemon、連接帳號與真正操作工具是不同步驟。缺少權限或環境時，清楚標示可讀的示範和未執行的操作。教學結束時，讀者應知道如何再執行、查版本文件、定位錯誤，以及需要時如何停止或還原。
