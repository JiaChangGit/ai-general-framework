# 如何問到會改變決策的問題

優先請使用者描述一個真實任務與現在的困擾，再問缺少的取捨。提供選項時，交代各選項的實際代價，也保留自由回答。

| 未知 | 有用的問題 | 回答會改變什麼 |
|---|---|---|
| 目標 | 完成後，你原本做不到的哪件事會變得可行？ | 交付範圍與驗收 |
| 方案假設 | 如果只用既有工具也能達成，你還需要自行開發哪一部分？ | 是否新增平台或抽象層 |
| 使用情境 | 請選一個這週真的會使用的任務。 | 第一條完整工作流程 |
| 成本 | 品質、等待時間與付費用量衝突時，這次優先哪個？ | 深度、模型與委派 |
| 自主性 | 哪些操作可以直接完成，哪些需要先展示結果？ | 寫入與外部操作邊界 |
| 完成標準 | 請描述一個你會認為失敗的結果。 | 負面案例與停止條件 |

提醒缺漏時說清楚後果。例如：「批次改名可能產生同名檔案；需要決定遇到衝突時整批停止，還是略過該檔。」不要泛稱「還要考慮安全性、效能、擴充性」。

一輪討論結束後，檢查是否仍有會造成返工的不同理解。已明確的小事由代理判斷，不為每個可逆選擇再開一輪訪談。
