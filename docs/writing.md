# 自然、能用的工程文字

這裡把「沒有 AI 味」落在可檢查的閱讀品質：讀者知道在談誰、為什麼、根據什麼，以及下一步能做什麼。目標是讓工程內容清楚可信；不以猜測作者身分或 AI detector 分數驗收。

## 先決定讀者需要什麼

同事間回覆、公開教學、commit 與設計文件需要的背景不同。寫給已參與討論的人，先說決定與影響；寫給陌生讀者，補足理解該結論所需的前提。不要只用職稱推斷知識，也要考慮他是否熟悉這個專案與機制。

使用 `write-engineering` 時，代理應保留原來的技術意思，再調整表達。數值、否定、規範強度、適用條件、來源、symbol、命令與連結都不能因為改得順口而變質。缺少證據時縮小主張，或明確保留未知。

## 寫作與校閱原則

1. **用具體行為說明影響。** 不只說「提升穩健性」，要交代什麼條件下、哪個元件採取什麼動作，解決哪個問題。
2. **先確立話題。** 說清楚角色、動作、對象與結果；切換 CPU、執行緒、裝置或時間點時重新交代，避免「它」「此時」失去指涉。
3. **讓推理連得起來。** 「因此」要有足夠理由，「不過」表真正轉折，「如果」交代有效條件。需要時拆句，不以一串連接詞硬接多個原因。
4. **保留穩定術語。** 使用自然的台灣語句，正式名稱與 API 保持精確。必要英文就近解釋；後文不為避免重複而任意換名，也不把翻成繁體當成完成中文校閱。
5. **形式跟著內容走。** 過程與理由用段落，平行項目用清單，需要比較才用表。段落保持焦點，但不強制每段固定句數、三個重點或一張圖。
6. **刪掉沒有作用的文字。** 移除空泛強調、裝飾性結尾、無用背景與模板殘留。真正有用的限制、對照、回顧與不確定性仍應留下。
7. **檢查陌生讀者能否使用。** 先看他能否找到問題、前提、理由、限制與下一步，再由熟悉領域的人核對技術。AI 可協助找歧義，但不是真人理解的證明。

例如：「透過優化佇列機制，顯著提升系統可靠性。」沒有說明做了什麼，也沒有支持「顯著」的數據。如果原始碼與重現支持，可改成：「先檢查整批工作是否有足夠容量，再入列。容量不足時保留原有佇列，讓呼叫端能確認這批工作尚未被接納。」

這是表達方法，不是全庫替換規則。禁止某個字、破折號或否定句不能保證文章清楚；刻意加錯字、虛構經驗或隨機改節奏也不能改善工程內容。

## Commit 與 PR 留下修改的理由

遵循目標專案的語言和貢獻慣例。先交代觸發問題與影響，再說選擇這個改法的理由、現在的行為及相關驗證。對日後維護者有用的取捨應保留；曾經討論過的所有方案與聊天過程不必照搬。

簡單變更可用一兩段完成，不要求每筆 commit 都填固定小節。描述「哪些檔案被改」不足以保存理由；「優化流程」也無法解釋某段程式為何存在。回歸測試、效能數字、`Fixes` 或上游測試標籤都要有實際依據。
