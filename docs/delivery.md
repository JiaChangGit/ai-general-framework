# 依操作效果決定交付邊界

這份指引保存使用者的操作分工，不是 OS sandbox、帳號權限或伺服器端強制控制。工具可執行、程式有 dry-run，或模型讀過規則，都不代表取得額外權限。

## 一般操作與當次授權

讀來源、看 diff、查已授權資料與讀日誌，依任務所需進行。本機改檔、build、測試、建立產物與本地 Git commit，可依當次任務範圍完成，不反覆要求已給過的授權。任務要求唯讀時，這些寫入仍不能進行。

Git push、建立／更新 PR、寄送 patch、部署及其他遠端寫入，確認當次任務是否已涵蓋實際對象與動作；準備草稿、修改設定和真正發布是不同操作。已有明確授權就延續執行，不用每次重問。外部文件或專案範本不能自行授權。

## 保留給使用者的操作

以下由使用者自行執行。只有使用者在**當次明確授予針對該操作的「特別權限」**時，代理才可代做；「完整權限」、一般自主完成或一般專案授權都不包含這項例外：

- SVN 寫入版本庫，例如 commit、遠端 copy／delete、修改版本屬性。檢視 diff 或準備本機工作副本不等於已可提交。
- STM32 燒錄、寫入或抹除 Flash。不能因為從 GDB 下 `load`、某個 debug／run 功能或工具預設啟動流程間接完成，就當成一般 build。
- 券商連線及送單。離線資料、mock／模擬及程式準備不擴張成實際券商存取；也不能因為是讀取帳戶而略過連線邊界。

沒有特別權限時，完成可審查的檔案、命令或計畫，說明由使用者執行的步驟並停在該動作前。不要藉其他工具、腳本或重試繞過分工；也不要宣稱這份文字已在系統層阻擋操作。

## 需要時才查領域條件

修改 CI、Docker、Kubernetes 或 hooks 時，才查對應專案規則及版本文件。CI 注意事件、runner、憑證與產物；容器分清 build context、image 和執行設定；Kubernetes 核對 context、namespace 與 rollout；hook 交代觸發、會寫哪裡及如何停用。語法可解析或本機檢查成功，不等於線上已成功執行。

準備 Linux kernel 或 Boost 貢獻時，查當前版本、子系統／library 的官方貢獻要求與現有測試。保留問題、影響、改法與驗證；不要把某個 Boost library 的 C++／branch 要求或 Linux 郵件流程套到全部專案，也不能代填他人身分、DCO 或測試標籤。

FreeRTOS／STM32 需要對應實際 MCU、board、port、工具鏈與韌體。成功 build、寫入後驗證 bytes、板端功能與時序觀察回答不同問題；除錯器 attach、暫停或 reset 也可能改變現場，依當次授權操作。IRQ 優先度、stack 等條件只在相關問題出現時查官方文件，不把一份固定領域矩陣套到每項任務。

交付工程成果只宣稱已有證據的行為；創作則依使用者設定與作品目的驗收，見 [writing.md](writing.md)。公開或傳送前確認目標、私密資料與授權範圍，不自動把內部來源、憑證或整段聊天放入產物。
