# 寫作短版

寫說明文件、README、教學、報告或交接檔之前讀這一頁。長篇文件、小說與創作、使用者要求校閱文字時，讀完整的 writing 指引。commit 訊息與一兩句的回報不用讀，照專案慣例寫清楚為什麼改、怎麼驗證即可。

- **動筆前查偏好與依據。** 語言、圖解或教學的偏好用 `agf profile show --root <專案目錄>` 查；README、舊文件和程式、執行結果不一致時，以執行結果與目前的原始碼為準，並在回報裡指出差異。
- **先講話題，再講誰做了什麼。** 條件放前面，主詞靠近動詞；一句只放一個新概念，太長就拆。
- **用動詞，不用名詞化。** 「進行驗證結果之檢查」寫成「檢查驗證結果」。
- **每句都要帶來資訊。** 刪掉後讀者什麼都沒少的句子就刪；不寫空泛的形容詞、不湊對稱的正反兩面。
- **不寫沒有根據的話。** 沒跑過的不說通過，推論標成推論；數字回到原始輸出核對，「可能」不改成「一定」。
- **改寫只用原稿的事實。** 寫完逐項對照：條件、先後順序、誰做的、「可以／必須／不得」與確定程度都不變；舉情境時也一樣。原稿沒說的因果、時序與主詞不補，需要時寫明原稿沒說。
- **一個概念一個名字。** 不為了變化把 client 一下寫用戶端、一下寫客戶端；API、命令、檔名保持原樣。
- **用台灣的說法。** 「最佳化」不寫「優化」、「連接埠」不寫「埠」；專有名詞第一次出現時用白話解釋。
- **主體要清楚。** 換元件、換時間或從作者改談讀者時交代一下；不讓「它」「我們」指不清。
- **比喻不能藏住事實。** 「逾時錯誤吞噬了工作」寫成「逾時後，這筆工作沒有加入佇列」。

AI 味的七項徵兆（流暢但沒內容、歐化長句、話題與人稱亂跳、資訊太密、死物配活物動作、外地用語、主詞動詞太遠）的完整說明與實際例子在完整版的校閱清單。清單只用來找候選，命中了也要看語境。
