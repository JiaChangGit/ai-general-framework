# 框架分析：優缺點與之後的方向（2026-11）

2026-11-17。依使用者列的標準逐項檢查，證據來自三處：

- **S8 的盤點與三個對照實驗**（2026-11-16，在 Raft KV store 專案裡做），見 [studies/raft-kv-2026-11/analysis/report.md](../studies/raft-kv-2026-11/analysis/report.md)。
- **這次（S10）用框架完成一整輪複查的實際經驗**：找到並修正 Raft 專案的三個缺陷、改寫十幾份文件、做了一次獨立審查與一次中文校閱，途中撞到一次 5 小時的用量上限。
- **外部研究**：熱門開源專案、官方文件、論文與演講，見 [studies/README.md](../studies/README.md)。報告裡每一條都標了實際讀過或只看到摘要。

限制先說：實驗樣本小、只在一個專案和一個宿主（Claude Code）上做；外部研究由網頁讀取工具摘錄，數字引用前要回原文核對。下面的判斷是方向，不是定論。

## 摘要

1. **內容大多是對的，問題在「什麼時候被用到」和「靠文字擋不住的事」。** S8 證實 skill 從沒被宿主機制叫用、規則入口沒接上；那兩件事在 S8 後續已修。這次又看到：寫在交接與規則裡的提醒（不要 `pkill -f`、不要 push、不要 `cd` 進框架）照樣重犯，真正擋住的是可以執行的檢查。官方文件也這樣說：CLAUDE.md 是建議，非發生不可的事要用 hook。
2. **常駐的文字要少。** 一篇 ETH 的研究發現，repo 的 context 檔（AGENTS.md 一類）整體上沒有提高成功率，成本卻多了兩成以上；S8 實驗 A 的框架組也多花了 39%。規則只該放「會改變行為」的句子。
3. **skill 少而專比多而全好。** SkillsBench：2～3 個專注的 skill 平均 +18.6 個百分點，4 個以上只剩 +5.9，「完整說明」型的反而 −2.9；但軟體工程類只有 +4.5。框架的 6 個 skill 方向正確，再加新的要謹慎。
4. **跨 session、跨模型、用量上限，是使用者最常付出代價的地方，框架原本幾乎沒有對策。** 沒有任何熱門專案為「用量突然用完」設計專門的機制；能救回來的只有已經寫在磁碟上的東西。
5. **「做過一次的檢查」會悄悄壞掉。** Raft 專案的示範腳本、兩篇教學的重現、乾淨環境的重建，都在之後的階段壞了，因為它們不在每次都跑的驗收裡。框架的驗證指引沒有提醒這件事。

這次依這些發現做的修改列在最後一節與 [CHANGELOG.md](../CHANGELOG.md)。

## 逐項

每項寫：現況、優點、缺點、這次改了什麼、之後的建議。

### 1. SKILLS、SCRIPTS、REFERENCE、MCP、CLI 沒有重疊、衝突、誤觸、沒觸發、多餘

- **現況**：6 個專用 skill（加上這次的第 7 個，只能由使用者叫用）、按需讀的四份指引、`agf` CLI 的 14 個子命令、templates 與 evals。
- **優點**：skill 描述短（6 段共約 1,500 字元，遠低於 Claude Code 每段 1,536 字元的上限）；S8 的實驗裡不該用時沒有誤觸；`agf audit` 檢查結構與連結。
- **缺點**：S8 證實「沒觸發」是主要問題（已在 S8 後續改善措辭，量測差距在雜訊內）。這次 session 從專案的上一層啟動，專案的 skill 完全沒列出，只能直接讀 `SKILL.md`：skill 能不能被用到，取決於使用者從哪個目錄啟動。`agf` 的 14 個子命令在 Raft 專案只用過 3 個，那個專案還自己重寫了一份限時限量的執行器。
- **這次改了**：新增的 `align-with-me` 用 `disable-model-invocation`，不進模型的 skill 清單，不會和其他 skill 搶觸發。
- **之後**：（高）在 `agf project status` 加一行：偵測 session 可能從上層目錄啟動時（例如上層有 `.claude/` 而專案的 skill 不在上層），提醒使用者 skill 不會被列出。（中）記錄各專案實際用到的子命令，一年都沒人用的考慮移到範本或刪掉。MCP 在這幾個專案都沒用到，沒有證據可以評。

### 2. 自然地利用多種模型、跨部門合作；交接與長期記憶

- **現況**：`workflow.md` 規定交接要有目標、版本、決定、驗證、下一步、範圍，以及接手者要自己跑的核對命令（S8 後續加上）。
- **優點**：這次的流程真的跨了三種角色：主 session、換模型的獨立審查（儲存層審查找到 1 個健壯性缺陷、8 個測試缺口、5 處文件不符）、換模型的中文校閱（找到 3 個事實錯誤）。指定模型的子代理比切換主模型便宜，也不打斷主線。
- **缺點**：原本沒有談用量、快取與換模型的成本。這次一次開了 4 個子代理，幾個小時內撞到 5 小時上限，審查做到一半中斷；使用者換模型後要我「再試一次」，如果沒有落盤的進度，就得全部重讀。長期記憶靠宿主的自動記憶，框架只給原則。
- **這次改了**：`workflow.md` 新增「續接、換模型與用量」：哪些時刻要先寫交接檔、換模型會讓快取失效、子代理各自從零讀起、被上限打斷時接著用原本的子代理、長時間命令要能續跑並與 session 分開執行。常駐規則加一條「續接與用量」。
- **之後**：（中）`agf task record` 加一個 `--checkpoint` 的快速模式，只寫「已完成（commit）、進行中、下一步」三欄，讓寫交接的成本低到每個里程碑都願意寫。（低）用宿主的 usage 紀錄，量一次「有交接檔 vs 沒有」在換模型後的 token 差。

### 3. 個人化：視覺化 trace、文件沒有 AI 味、commit 寫清楚為什麼、台灣中文通順、會教人

- **現況**：`writing.md` 涵蓋話題、人稱、名詞化、主詞動詞距離、空洞句與 commit；`profile` 合併偏好；`trace-code`、`guide-learning` 依讀者選圖與示範。
- **優點**：這次照 `writing.md` 寫的十幾份中文文件，換模型校閱的結論是「AI 味很輕」；必改的 6 項裡，5 項是事實或數字寫錯，只有 1 項是新手會卡住的說明缺口，沒有一項是文字的 AI 味。教學類 skill 的十節樣板，讓 bug 教學有固定的「怎麼發現、怎麼找到根因」。
- **缺點**：使用者的七項 AI 味標準散在指引各段，沒有一張可以照著查的清單；同一概念換名字（client／用戶端、落盤／持久化）與外地用語（埠、優化）沒有被提到。規則式的自動檢查在 S7 證實幾乎沒用（只找得到約 4% 的問題），不能拿來當門檻。
- **這次改了**：`writing.md` 新增七項的校閱清單，每項附一個實際改過的例子，並補上「一個概念一個名字」與「數字回查來源」。
- **之後**：（中）把校閱交給另一個模型時，給它這張清單和一份抽查事實的任務（這次的做法）；這比任何規則式檢查有用。（低）`evals/writing-cases.json` 加入這次的實例。

### 4. 降低 token 消耗

- **現況**：按需讀指引、有界的搜尋與摘錄工具、重用腳本。
- **優點**：skill 描述的常駐成本很小。
- **缺點**：S8 實驗 A 的框架組多花 39%（品質 47 vs 44，滿分 48）。這次最大的浪費不在文字，而在：4 個平行子代理、撞上用量上限後的重試、以及 RTK hook 改寫命令後，自動權限審查要求原樣重送（這次發生了 2 次，每次多一個來回）。
- **這次改了**：常駐規則的字數維持不變（1,310 → 1,316 字），換成更直接的句子，多了三條這次證實需要的規則；子代理與換模型的成本寫進 workflow。
- **之後**：（中）用 S8 的實驗方法量一次新規則與舊規則的成本與品質，再決定要不要進一步刪減。（低）在 adapter 註明 RTK 與自動權限審查的互動，請使用者決定要不要在自動模式下停用改寫。

### 5. 降低 bug 出現

- **現況**：最小修改、依風險驗證、`review-change`。
- **優點**：這次的三個缺陷都是被「可以執行的檢查」抓到的：一個單元測試、一次乾淨環境重建、一次植入錯誤的審查。框架鼓勵的「先寫會失敗的測試」與「獨立審查不給預期答案」都有效。
- **缺點**：框架沒有提醒「只做過一次的檢查會壞」。Raft 專案的示範從 S5 起就跑不完、兩篇教學的重現從 S4、S5 起就失效、乾淨重建會失敗，都沒人發現。
- **這次改了**：常駐規則的「驗證」一條加上：宣告完成前，示範腳本、文件裡的命令、在乾淨環境重建也要重跑。
- **之後**：（中）`templates/quality.example.json` 加一個「定期」檔位，列出示範、文件命令與乾淨重建，讓專案把它們接進 `agf check`。

### 6. 有效率地 debug、找出根因

- **現況**：`debug-root-cause` 用能區分假設的觀察縮小範圍，把緩解和根因分開。
- **優點**：方法和實際有效的做法一致。這次查 S5 審查留下的「無法解釋的失敗」，先找能區分假設的觀察（測試本身不依賴時間、400 次並行不再失敗、當時的副本在 4.3 GB 的 tmpfs 上），判斷剩下的假設已無法驗證就停手，沒有無限追查。
- **缺點**：研究（Failure as a Process，1,794 條軌跡）指出：決定性的錯誤平均在第 7 步，第一個看得見的訊號在第 16 步；26% 的失敗執行會拿捏造的證據宣稱成功。skill 沒有強調「先驗證前提」與「宣稱成功要附證據」。
- **之後**：（中）`debug-root-cause` 的開頭加一句：先列出這次調查依賴的前提，逐一用觀察確認；宣稱修好時附上修正前失敗、修正後通過的輸出。

### 7. Grill me，和我對齊想法

- **現況**：`workflow.md` 有一段 grill 的說明。
- **優點**：這次開頭問了 4 個問題，每題附建議與代價，使用者一次答完、之後追加一個要求，整個 session 沒有再為已決定的事重問。
- **缺點**：沒有一個使用者可以直接叫用的入口；要對齊多深、什麼時候停，全靠模型自己判斷。
- **這次改了**：新增 `align-with-me`：先查材料與既有能力、一輪最多四題且先問上游的、每題附建議、決定寫進專案保存決定的地方、清單確認後才動手。
- **之後**：（低）用 `evals/host/` 量一次「使用者打 /align-with-me」與「只說先問我問題」兩種情況的行為差別。

### 8. 提醒開發者還缺什麼、誤解了什麼

- **現況**：規則要求主動指出矛盾、漏項與誤解，並先查框架已有的東西。
- **優點**：這次在動手前就指出「AI 痕跡」有三種做法、影響不同，讓使用者選；校閱發現的數字矛盾（14 還是 16）也回頭修正了文件。
- **缺點**：寫成文字的提醒擋不住重複的錯。
- **之後**：（中）把重複出現的坑寫成可以執行的檢查：guard hook 已經處理了 push、PR、`pkill -f` 與受保護路徑；下一個候選是「`cd` 進了別的 repo」的提醒。

### 9. 不會過度思考

- **優點**：S8 的實驗沒有看到框架讓 session 失控；這次在「無法解釋的失敗」上依證據停手。
- **缺點**：沒有量化的證據。
- **之後**：不改。

### 10. 不會代碼膨脹

- **優點**：templates 不會自動部署；這次的 guard hook 是一個只用標準函式庫的檔案，沒有新的相依。
- **缺點**：工具沒被想到時，專案會自己重寫一份（Raft 專案的 `capped_run.py`），這是間接的膨脹。
- **這次改了**：常駐規則的「改程式」一條換成 ponytail 式的五個問題。
- **之後**：同第 1 項：讓沒人用的子命令退場。

### 11. 明確的邊界（資安隱私、CI/CD、hooks、腳本、容器）

- **現況**：`delivery.md` 依操作效果判斷授權；原生權限範本（S8 後續）；adapter 誠實標示哪些實測過、哪些沒有。
- **優點**：框架沒有假裝文字能隔離。
- **缺點**：S8 實測：專案的 deny 規則只在 session 從那個目錄啟動時生效；`git -C . push` 不符合 `Bash(git push:*)`；`python3 -c` 能寫進受保護的目錄。這次 session 從上一層啟動，靠的是上一層的 deny 規則，它確實擋住了寫入框架主目錄（所以這次的修改在 worktree 上做）。hooks 原本標示「未測試」。
- **這次改了**：`templates/claude-guard-hook.py`：PreToolUse hook，擋下各種寫法的 `git push`（`git -C`、`sh -c`、`env`、`rtk` 前綴）、建立或合併 PR、`pkill -f`／`killall`、寫入受保護路徑（檔案工具與常見的 shell 寫法）。10 個單元測試；用 Claude Code 2.1.325 的無頭 session 實測，`git -C <dir> push` 與寫入受保護目錄都被擋下，模型照實回報、沒有嘗試繞過。adapter 另記一筆 `guard_hook`：已實測的情況與沒測過的部分（原本「跑品質檢查的 Stop hook」那一筆仍是未測試）。commit 前看暫存範圍的規則寫進 `delivery.md` 與常駐規則（這次我自己就犯了一次：重設 index 後，先前暫存的刪除跟著進了錯的 commit）。
- **之後**：（高）由使用者決定是否把 guard hook 裝進使用者層級的 `~/.claude/settings.json`，讓它不論從哪個目錄啟動都生效；裝之前先在一個專案試用一陣子。（中）CI、容器在這幾個專案都沒用到，維持現狀，不擴充。

## 之後的優先順序

1. 決定 guard hook 要不要裝到使用者層級（需要使用者決定；影響所有 session）。
2. `agf project status` 偵測「session 可能從上層啟動、skill 不會被列出」。
3. 在另一個專案用一陣子新規則，再用 S8 的方法量一次成本與品質。
4. `debug-root-cause` 加「先驗證前提、成功要附證據」。
5. `agf task record --checkpoint` 的快速模式。
6. 品質範本加「定期」檔位。
7. 子命令用量紀錄與退場。

## 方法與限制

- 這份分析的作者，也是這次修改框架的人；修改已交給沒參與的模型審查（結果見 CHANGELOG），但評分與判斷仍偏向作者自己的經驗。
- 只有 Claude Code 一個宿主；Codex、Gemini CLI、OpenCode 上的行為沒有驗證。
- 外部數字多數是各專案作者自己量的（ponytail、rtk），或單一 benchmark（SkillsBench）；引用時照實寫出來源與限制。
