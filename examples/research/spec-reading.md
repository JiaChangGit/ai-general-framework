# 從一個輸入帶讀小規格

目標：解釋批次何時被拒絕，以及拒絕後應保留什麼狀態。來源是 [Batch Queue 教材規格 0.1](mini-spec.md)，不是 Python 輸出的描述。

先固定假設：`capacity=2`、`pending=["A"]`、`jobs=["B", "C"]`，且符合規格前提。這些數值是教學輸入，不是實測資料。

| 閱讀位置 | 此時為何查看 | 得到什麼 |
|---|---|---|
| 開頭及 §2 | 確認規則是否適用這個模型 | 單一呼叫者、同步、記憶體內；既有工作與輸入的身分明確 |
| §1 | 確認要求的強度 | 「必須」是本文件的必要要求 |
| §3 的前兩項 | 排除較早的拒絕條件 | 批次非空，`B`、`C` 彼此及與 `A` 都不重複 |
| §3 第三項 | 判斷整批能否被接納 | `1 + 2 > 2`，應回傳 `capacity` |
| §4 | 判斷拒絕的狀態效果 | 完整 `pending` 必須仍為 `["A"]` |
| §5 | 確認不能延伸哪些結論 | 無法由此推論併發、落盤或後續工作執行 |

閱讀路線是為了查證結論，不代表實作真的用相同函式或資料結構執行。接著看 [queue_walkthrough.py](../learning/queue_walkthrough.py)，才能比較 `Queue` 與 `BuggyQueue` 是否維持這項要求；執行後又能取得特定輸入的 runtime 觀察。三者的證據範圍不同。

如果改成 `jobs=["A", "B"]`，重複識別碼與容量條件都成立；§3 要求先回傳 `duplicate`。若改成同時有兩個呼叫者，本規格沒有提供判定規則，應查其他規範或補定義，不能假設這份程式已處理同步。

帶讀可直接展示推理；練習時則可先請讀者預測一個改變前提的案例。驗收教材看來源、算式與結論是否一致；驗收真人理解仍需要實際互動，不能由 AI 答案替代。
