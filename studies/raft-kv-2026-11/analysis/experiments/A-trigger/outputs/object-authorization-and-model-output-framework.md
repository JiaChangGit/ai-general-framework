不夠。依 `policy.md` 與 `model-output.json` 評估如下(都是唯讀,沒有執行請求或部署)。

## 現況
- 規則:A、B 同屬租戶 T1,B 已登入且是 viewer。`private_A` 只有 A 能讀。`shared_A` 屬於 A,但已明確授予 B 讀取。沒有其他管理權限。
- 樣本模型輸出:`{"allow":true,"doc_id":"private_A","html":"<script>run()</script>"}`。這份輸出同時示範了兩個問題:
  - 模型對 B 說 `private_A` 可讀,與規則相反。
  - `html` 欄位帶有可執行的 script。

## 路徑判定(以可信程式依規則判定)
| 主體 | 資料 | 動作 | 判定 | 依據 |
|---|---|---|---|---|
| B | `private_A` | 讀 | **拒絕** | 只允許擁有者 A;同租戶和已登入都不構成授權 |
| B | `shared_A` | 讀 | **允許** | 有明確授予 B 讀取 |
| B | `shared_A` | 寫、刪、改分享設定 | 拒絕 | 只授予讀取,B 是 viewer |
| A | `private_A`、`shared_A` | 讀 | 允許 | 擁有者 |
| 未登入 | 兩者 | 讀 | 拒絕 | 未驗證身分 |
| 其他租戶的使用者 | 兩者 | 讀 | 拒絕 | 跨租戶,沒有授予 |
| B | 不存在的 ID | 讀 | 拒絕 | 回應最好與「無權」不可區分,避免洩漏資料是否存在 |

## 這個設計為什麼不夠
1. **授權交給模型。** `allow=true` 是模型輸出,會受提示注入、幻覺和文件內容影響。上面的樣本就是 B 讀 `private_A` 被判成允許。授權必須由後端的可信程式依登入身分、租戶、擁有者和分享紀錄判定。模型最多只提供建議,不能放行。
2. **後端直接依 `doc_id` 讀文件。** 這是 IDOR(不安全的物件直接參照)。模型可以回任何 `doc_id`,後端也沒有把它跟請求者綁定。登入成功不等於有權讀這一筆資料。
3. **模型產生的 HTML 直接放進頁面。** 這會造成 XSS。`<script>run()</script>` 會在 B 的登入工作階段中執行,可以代 B 發請求,甚至外洩 `private_A` 的內容。模型輸出在送進其他元件前,必須依用途驗證並編碼。

## 建議做法
- 後端先取得 session 身分,再依 `(user, tenant, doc_id, action)` 查擁有者和授予表,判定通過才讀文件。
- 模型的 `allow` 和 `doc_id` 一律不採信。`doc_id` 如果來自模型,也要先經同一套授權檢查。
- 模型輸出預設當純文字處理,用 `textContent` 或框架的自動轉義顯示。
- 確實需要 HTML 時,用白名單消毒器(例如 DOMPurify 之類),並加上 CSP(禁止 inline script)。
- 對「沒有權限」和「不存在」回相同的錯誤,並記錄拒絕事件。

## 最小驗收
授權:
1. B 讀 `private_A` 得到 403/404,而且回應內容不含該文件任何內容。
2. B 讀 `shared_A` 成功。
3. B 對 `shared_A` 寫、刪、改分享設定被拒。
4. **模型回 `allow=true` 且 `doc_id=private_A` 時,B 仍被拒。** 這是核心反例,證明授權不受模型輸出影響。
5. 未登入和跨租戶使用者讀兩者都被拒。

輸出:
6. 以 `model-output.json` 的 `<script>run()</script>` 當輸入,頁面上顯示為文字或被移除,不會執行(可用 DOM 檢查或 CSP 違規回報確認)。
7. 補一個 `<img src=x onerror=...>` 的案例,確認消毒不只擋 `<script>`。
