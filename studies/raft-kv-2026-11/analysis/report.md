# ai-general-framework 分析報告（S8）

2026-11-16，`claude-opus-5-5`。依使用者列的 11 項標準（原文在 `docs/ROADMAP.md`「S7、S8 的依據」）。
證據有四類：本專案的框架經驗紀錄 L01～L55、兩份獨立審查、S7 報告，以及 S8 的元件盤點與三個實驗。實驗的做法與原始紀錄在 [experiments/](experiments/)，盤點在 [inventory.md](inventory.md)。
框架只讀，沒有修改；下面所有建議都只是建議。

## 摘要

**框架的內容大多寫得對，問題出在「該用的時候沒有被用到」。** 寫作、交接、驗證、邊界，框架都有清楚的指引；可是在 Claude Code 上，它們能不能發揮作用，要看入口有沒有接上。

- **skill 從沒經由 Skill 機制被呼叫。** 實驗 A 的 12 次 session 裡，Skill 工具一次都沒被呼叫。框架組是照 `AGENTS.md` 的一句話，自己去讀 `.agents/skills/…/SKILL.md`（那是給 Codex 的副本）。
  該用 skill 的 4 個情境讀到了 3 個（`read-research` 沒讀），不該用的 2 個沒有誤觸。
- **既有專案的規則入口沒有接上。** 新目錄安裝後，`CLAUDE.md` 有兩行 import，規則每次都會載入；本專案原本就有 `CLAUDE.md`，框架保留它、沒有加 import，所以規則與指引不會自動載入（L52 的根本原因）。
- **品質略好，成本明顯較高。** 實驗 A 盲評：框架組 47／48，對照組 44／48；框架組花費多 39%、token 多 26%。框架 2026-11-09 自己的文字層對照是「品質相同、多 14.4% token」，方向一致。
- **交接文件對強模型有用，弱模型會把它當答案。** 實驗 B：有交接文件的 Sonnet 實際執行了所有核對（8／8）；有交接文件的 Haiku 只照抄交接文件的說法、沒有驗證（5.5／8）。
  沒有交接文件時，兩者都去讀路線圖自救（7.0、6.5）。
- **入口點名，指引才會被讀。** 實驗 C：`CLAUDE.md` 加一行點名寫作指引，2 個案例裡 1 個真的去讀了；不點名時 0 個。品質差異被雜訊蓋過（每格只跑一次）。
- **隔離比想像中難。** 兩次實驗都被受試者「走出自己的目錄」污染：一次讀了兄弟目錄，一次照 `CLAUDE.md` 的絕對路徑讀了原專案的交接文件。框架的評測說明沒有提醒這兩件事。

**只能改三件事的話：**

1. **接上規則入口**（標準 1、3）。安裝到已有 `CLAUDE.md` 的專案時，提示並在使用者同意後加入兩行 import；`agf project status` 把「規則沒有被匯入」列為警告。證據：D0、盤點 §3、L52、實驗 C。
2. **依宿主寫 skill 的用法，並把觸發列入回歸評測**（標準 1、4）。Claude Code 上不要叫模型去讀 `.agents/skills/` 的檔案，讓 skill 走宿主的 Skill 機制；
   用這次的 `run_session.py` 加上 `scenarios.json`，定期量「該用卻沒用」與「不該用卻用了」。證據：實驗 A。
3. **把「核對」寫成接手者要執行的命令，把隔離寫成可執行的預檢**（標準 2、8、11）。交接樣板要求列出接手者自己執行的命令與預期結果，不要只寫結論；
   評測說明加上「實驗宿主的預檢」：能否登入、會不會回報用量、看得到哪些 skill、能不能讀到上層與兄弟目錄、文件裡有沒有原專案的絕對路徑。證據：實驗 B、L54、L55。

## 逐項

每項依序寫：現況（框架說怎麼做）、證據、優點、缺點、建議（優先序）、信心。

### 1. SKILLS、SCRIPTS、REFERENCE、MCP、CI 沒有重疊、衝突、誤觸、沒觸發、多餘

- **現況**：6 個專用 skill、按需讀的指引、共用的 `agf` 工具；README 寫「專用 skills、按需 references、共用工具」。
- **證據**：盤點；實驗 A（觸發 3／4、誤觸 0／2、Skill 工具 0 次）；實驗 C（點名後讀到 1／2）；L52、L23、L13。
- **優點**：`agf audit` 沒有錯誤；6 段 skill 描述合計只有 1,522 字元，常駐成本小；不該用 skill 時沒有誤觸；做簡報時框架組自己去讀了框架的簡報參考，按需參考有被正確用到。
- **缺點**：「沒觸發」是主要問題：既有專案沒有 import 規則；Claude 上靠模型自己讀檔，而不是宿主的 skill 機制；`read-research` 該用沒用；
  14 個 `agf` 子命令只有 3 個用過；`agf run` 早就有時間與輸出上限，S5 審查卻另寫了 `capped_run.py`（盤點 §3 第 2 點）。宿主層級另有 `debug`、`code-review` 等相近的 skill，這次沒有看到衝突。
- **建議**：（高）接上入口、依宿主寫 skill 的用法（見「三件事」）。（中）在 `project-rules.md` 用一行一個列出 `agf` 子命令的使用時機，讓模型在對的時候想到它們。（低）記錄本機的使用次數，找出真的沒用的部分。
- **信心**：已證實（單一專案、單一宿主、每情境一次）。

### 2. 自然地利用多種模型、跨部門合作；交接文件與長期記憶

- **現況**：`workflow.md` 規定交接要保留目標、版本、已決定事項、驗證狀態、下一步與操作範圍；模型與角色可互換。
- **證據**：L42（交接欄位照 `workflow.md`）、L49（跨模型接手順利）、L45、L22；實驗 B；L53（沒有明說就不會開子代理）。
- **優點**：照 `workflow.md` 寫的交接文件，讓不同的模型、不同的 session 能接手：本 session（Opus）從 Sonnet 審查者的交接接手順利；實驗 B 的 Sonnet 有交接文件時 8／8。
- **缺點**：較弱的模型會把交接文件當成答案，不去驗證（Haiku 5.5／8）；交接與入口檔裡的原專案絕對路徑，讓副本無法隔離，也可能讓接手者讀到過期或不同的版本；
  多模型的步驟（例如換模型評分）要使用者明說才會執行，否則被跳過（L53）。長期記憶靠宿主的自動記憶與專案文件，框架的 `agf task` 沒有用過，效果沒有證據。
- **建議**：（高）交接樣板加「接手者要親自執行的核對命令與預期結果」。（中）規格樣板加「模型分工」一欄，使用者核准規格時一併同意開子代理。（中）交接裡的路徑寫成相對路徑，或註明「這是原專案的位置」。
- **信心**：觀察（每個條件一次）。

### 3. 個人化：視覺化 trace、文件沒有 AI 味、commit 說明為什麼、台灣繁體中文通順、會教人

- **現況**：`writing.md` 涵蓋話題與人稱、名詞化、主詞動詞距離、空洞句、commit 的寫法；`profile` 合併個人偏好；`trace-code`、`guide-learning` 依讀者選圖與示範；`agf diagram` 產生圖。
- **證據**：S7 報告與實例；L52、L53；實驗 A 的 `learning-with-trace`（框架組讀了 `guide-learning`、明說答案是推論，盲評 8 分 vs 對照 6 分）；實驗 C。
- **優點**：寫作指引的內容涵蓋使用者七個 AI 味特徵中的六個，實測支持它「不設禁詞表」的立場；教學類 skill 在被讀到時確實讓成果更嚴謹。
- **缺點**：寫作指引在本專案從沒被讀到（S6 寫了四篇教學也沒讀）；`profile` 與 `agf diagram` 沒有用過，本專案的圖都是手寫 Mermaid；規則式的 AI 味檢查幾乎沒用（S7：只找得到約 4% 的問題）。
- **建議**：（高）寫作類的入口（專案自己的寫作 skill、交接樣板）第一步就點名 `guides/writing.md`。（低）不要把規則式的 AI 味檢查加進框架。
- **信心**：已證實（S7 有量化）；實驗 C 只是觀察。

### 4. 降低 token 消耗（類似 snippet 的 scripts）

- **現況**：按需讀指引、有界的搜尋與摘錄（`agf context`、`agf source`）、重用 scripts；README 承認首次對照「框架組用量較高」。
- **證據**：實驗 A（框架組 +39% 費用、+26% token；快取建立每次多 3.5k～11k）；框架 2026-11-09（+14.4%）；S7（規則式先篩只讀 6% 的字，卻只找到約 4% 的問題）。
- **優點**：常駐的 skill 描述很小；指引平常不載入。
- **缺點**：被 import 的規則（`AGENTS.md`＋`project-rules.md`）每個 session 都要付；框架組的回合數持平或多 1～3 次。省 token 的工具（`agf context`、`agf source`）在本專案沒有用過，效果沒有證據。
- **建議**：（中）把每次都載入的規則刪到只留會改變行為的句子，用同一套實驗量刪減前後的差別。（中）「snippet 式的 script」只在量過完整任務的用量與品質之後才收進框架。
- **信心**：已證實（實驗 A 的方向和框架自己的紀錄一致；樣本小，比例不可外推）。

### 5. 降低 bug 出現

- **現況**：最小修改、風險相稱的檢查、`review-change`；用原始失敗與回歸驗證成果。
- **證據**：兩份獨立審查（S1～S4、S5），S5 審查的 F1～F7；19 篇教學；L48。
- **優點**：`review-change` 是本專案唯一經由 skill 機制使用的框架 skill，S5 審查找出了真正擋住驗收的 F6、F7。
- **缺點**：本專案的 bug 主要靠專案自己的測試、mutation、模擬器與審查找到，框架的角色難以分離；「文件寫成完成，驗收其實沒跑完」（F1、L48）框架的指引沒有擋住。
- **建議**：（中）把「完成的定義」寫成可檢查的條件：沒有驗證產物（例如驗收通過後才建的 tag），就不能寫「完成」。
- **信心**：觀察（無法歸因到框架）。

### 6. 有效率地 debug、找出根因

- **現況**：`debug-root-cause` 用能區分假設的觀察縮小範圍，把緩解與根因分開。
- **證據**：本專案從沒用過 `debug-root-cause`（盤點）；實驗 A 的 `flaky-repeat-evidence`（兩組都 7／8，框架組讀了 `debug-root-cause`）；L46（S5 審查的根因來自「每次都停在同一個位置」的觀察）。
- **優點**：skill 的方法和本專案實際有效的做法一致：先找能區分假設的觀察，再孤立重現。
- **缺點**：在這個專案與這次實驗裡，看不出它帶來差別。
- **建議**：（低）把 L46 的經驗（看似環境問題的失敗，先看是不是每次停在同一處）當候選例子；要等第二個專案也出現才加。
- **信心**：觀察。

### 7. Grill me，和我對齊想法

- **現況**：`workflow.md` 只問會改變決策的未知，理解後執行。
- **證據**：本專案每個階段開頭的提問與核准流程；L52（S7 的選項在查框架之前就給了）。
- **優點**：只問關鍵問題、得到答案就做的流程，在本專案運作良好。
- **缺點**：對齊之前沒有先查「框架已經有什麼」，S7 差點重做一份已有的寫作規則。
- **建議**：（高）提出選項之前先查既有能力（框架的能力表、評測、指引），並把查到的東西放進問題裡。
- **信心**：已證實（一次）。

### 8. 提醒開發者還缺什麼、誤解了什麼

- **現況**：指出影響結果的矛盾與缺失條件；有材料先核對。
- **證據**：L52（框架沒提醒自己已有寫作指引與評測）；盤點（`agf run` 沒人想到）；L55（交接寫過的坑照樣重犯）；實驗 B（Sonnet 主動指出交接文件不見了、要核對）。
- **優點**：被讀到時，框架的規則確實會讓模型標出未知與缺口（實驗 A 的盲評裡，框架組較常註明「這是推論」）。
- **缺點**：框架不會提醒「你要的東西我已經有了」；寫成文字的提醒擋不住重複的錯。
- **建議**：（中）把會重複的坑寫成可執行的檢查或包裝好的命令（例如用 PID 停止背景工作的小腳本）。
- **信心**：觀察。

### 9. 不會過度思考

- **現況**：相關驗證足夠就交付，沒有新的觀察價值時說明缺什麼、不無限重試。
- **證據**：實驗 A 的回合數（框架組持平或多 1～3 次）與耗時（多 0～14 秒）。
- **優點**：實驗裡沒有看到框架讓 session 失控或無限重試。
- **缺點**：框架組平均多讀 1～2 個檔（`SKILL.md`、指引），有時對結果沒有幫助（例如 `trace-without-lesson` 兩組同分）。本專案整體拖得太久，但無法歸因到框架。
- **建議**：（低）沒有足夠證據提出修改。
- **信心**：觀察。

### 10. 不會代碼膨脹

- **現況**：維護指引要求改在最窄的位置；共用工具。
- **證據**：盤點（`agf/` 3,075 行、14 個子命令，本專案用過 3 個）；`capped_run.py` 與 `agf run` 重疊。
- **優點**：templates 不會部署到專案，只在需要時拿。
- **缺點**：工具沒有被想到，專案就會重寫一份（`capped_run.py`），這是框架造成的間接膨脹。
- **建議**：（中）同第 1 項：讓 `agf` 子命令在對的時候被想到。
- **信心**：觀察。

### 11. 明確的邊界（資安隱私、CI/CD、hooks、腳本、容器）

- **現況**：`delivery.md` 依操作效果判斷授權；README 明說文字規則與 hook 不冒充強制隔離；Claude 的轉接設定寫明 hooks「尚未實測」。
- **證據**：盤點 §3 第 6 點；L50（工作目錄漂進框架）；D0（環境變數裡有宿主的訊息通道）；實驗 A 第一次嘗試（讀兄弟目錄）；實驗 B 第一次嘗試（讀原專案）；
  實驗 B 的 `ps`（看得到主持實驗的 session 與命令列）；權限探測（Read 的禁止規則也約束 Glob）。
- **優點**：框架誠實地區分「建議」與「強制」，沒有假裝文字能隔離。
- **缺點**：真正的強制靠使用者自己手寫（本專案的 deny 只擋 `Edit`，不擋 `Write` 或 Bash 寫檔）；框架沒有提醒：Read 不限於工作目錄、絕對路徑讓副本不隔離、
  子行程會繼承宿主的環境變數、`ps` 會露出其他 session。CI、容器、hooks 在本專案都沒有用到，沒有證據。
- **建議**：（高）`agf project install --host claude` 可選擇產生一份宿主原生的權限設定範本（禁止寫入受保護的目錄、禁止 push），並標明它管得到與管不到的範圍。
  （中）評測與代理執行子行程時的隔離清單（見「三件事」第 3 點）。
- **信心**：已證實（多個實例），但只在一個宿主上。

## 方法與限制

- 每個條件只跑一次；觀察到的差異可能是雜訊，不能推成觸發率或穩定的成本比例。
- 受試者只有 Claude 的 Sonnet 5.5 與 Haiku 5.5；評分者是 Opus 5.5，和設計實驗、寫了大部分證據的我同一個模型。盲評看不到組別，但成果本身可能透露指引的痕跡。
- 受試的 session 載入了使用者的全域設定（RTK hook、全域 `CLAUDE.md`、使用者層級的 skill），兩組相同。
- 兩次隔離缺陷都在執行中發現；受影響的嘗試保留為紀錄，不納入比較，修正寫在各實驗的 README。
- 花費與 token 是 CLI 回報的估算，不是帳單。
