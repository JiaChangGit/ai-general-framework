**結論：不夠，兩處都不能這樣做。**

## 依據
- `policy.md`：A、B 同屬租戶 T1，B 已登入且是 viewer。`private_A` 只有擁有者 A 能讀。`shared_A` 的擁有者是 A，已明確授予 B 讀取。B 沒有其他管理權限。
- `model-output.json`：`{"allow":true,"doc_id":"private_A","html":"<script>run()</script>"}`。
- 這份輸出正好是反例。B 若請求 `private_A`，模型說 `allow=true`，但依規則應該拒絕。`html` 欄位裡還有可執行的 `<script>`。
- 我只讀了這兩份材料，沒有執行請求，也沒有部署。

## 為什麼不夠
1. **授權不能交給模型。**
   - `allow` 是不可信的輸出。模型可能被提示注入影響，也可能單純判斷錯。
   - 授權要由後端可信程式判定。它用已驗證的身分（B、T1、viewer）、資源的擁有者和分享紀錄，對這次要讀的文件做決定。
   - 「登入成功」只代表身分已確認，不代表有權讀這一份文件。
   - 模型的 `allow` 最多當作參考訊號，不能是放行條件。
2. **`doc_id` 也是模型輸出，不能信。**
   - 後端應只讀「請求中、經授權檢查的那個 ID」。
   - 不能改讀模型回傳的 `doc_id`。這份輸出就是請求別的文件的例子。
3. **模型產生的 HTML 不能直接放進頁面。**
   - 這會造成 XSS（跨站腳本，惡意腳本在使用者瀏覽器執行）。
   - 輸出要依用途處理：當純文字就做 HTML 編碼；真的要顯示富文本，就用白名單消毒器，再加 CSP（內容安全政策）限制腳本。
   - 最簡單的做法是不收模型的 HTML，只收文字或結構化資料，由前端自己渲染。

## 應允許與拒絕的路徑（B 為 viewer，租戶 T1）

| 路徑 | 預期 | 理由 |
|---|---|---|
| B 讀 `shared_A` | **允許** | A 擁有，已明確授予 B 讀取 |
| B 讀 `private_A` | **拒絕** | 只有擁有者 A 可讀；同租戶不等於可讀 |
| A 讀 `private_A`、`shared_A` | 允許 | 擁有者 |
| B 寫、改、刪、改分享 `shared_A` | 拒絕 | 只授予讀取，B 沒有管理權限 |
| B 讀不存在的 ID | 拒絕 | 回應要與 `private_A` 的拒絕無法區分（見下） |
| 未登入讀任一份 | 拒絕（401） | 沒有身分 |
| 其他租戶使用者讀任一份 | 拒絕 | 跨租戶 |

拒絕時，`private_A` 與不存在的 ID 建議回同樣的狀態碼和內容，避免洩漏文件是否存在。

## 最小驗收
1. **授權測試，不經過模型。**
   - B 讀 `shared_A` 得到 200。
   - B 讀 `private_A` 得到 403 或 404，回應不含文件內容。
   - 上表其餘拒絕路徑逐一確認。
2. **模型輸出不能改變授權結果。**
   - 讓模型分別回傳 `allow=true` 和 `allow=false`，再加上 `doc_id` 被改成 `private_A`。
   - 對 B 的結果都要和前面的授權測試一致。這是對應這份輸出的核心測試。
3. **輸出處理測試。**
   - 以 `<script>run()</script>` 和 `<img src=x onerror=...>` 當模型輸出。
   - 頁面不能執行腳本；如果採編碼，應看到字面文字。
   - 確認 CSP 標頭有設定。
4. **一條完整流程。**
   - B 登入，開 `shared_A` 成功，再試 `private_A` 被拒。
   - 同時看拒絕時的錯誤訊息是否讓人看得懂，且不洩漏內容。
