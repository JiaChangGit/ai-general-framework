**結論：這份清理稿不能用來概括兩種情境。** 它只留下 A 類，漏掉 B 類。

**證據**

- `original-v2.txt` 第 2、3 行是兩條規則。兩條都以「當裝置忙碌時，控制器必須先檢查工作種類與授權，完成檢查後，」開頭，差別只在結尾：
  - A 類工作：應拒絕請求。
  - B 類工作：應暫存請求。
- `cleaned.md` 第 2 行只有 A 類那一條，沒有 B 類。
- `conversion-note.txt` 說明原因：轉換器把相同前綴的段落當成重複，只保留第一筆。這兩條前綴相同，內容卻不同，所以 B 類被誤刪。這是轉換造成的資訊遺失，不是原文本來就只有一種情境。

**缺項與限制**

1. **B 類規則整條遺失。** 只讀清理稿，會誤以為忙碌時對任何工作都是拒絕。
2. **其他工作種類沒有規定。** 原稿只寫了 A 與 B。若還有 C 類或其他種類，原稿沒有給結果，要寫成「未指定」，不能補成拒絕或暫存。
3. **來源版本無法核對。** `cleaned.md` 第 1 行寫「來源宣稱為 Spec v2，無 hash 或頁碼對照」。這份文件的版本、errata 與出處都沒辦法獨立驗證。原稿的 "Spec v2" 也只是檔頭自稱。
4. **「應」的強度沒有定義。** 兩條都寫「應」，但材料裡沒有這份規格自己的規範用語定義。依 `read-research` 的 `specifications.md`，不能假定它等同 SHALL 或 SHOULD，也不能為了中文順口而改變強度。
5. **「暫存」的細節沒有寫。** 例如暫存多久、容量滿了怎麼辦、之後何時處理，原稿都沒說，所以這些也不能推論。

**建議**（我沒有改檔）

- 讀原稿時，把兩條合併成一句：忙碌時先檢查工作種類與授權，A 類拒絕、B 類暫存。
- 轉換器改成比對整句，不要只比對前綴。
- 要補規範強度或 C 類以後的行為，需要規格原文或更完整的來源。
