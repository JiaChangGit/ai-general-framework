**結論：不夠。** 這個設計把兩個信任邊界都交給模型輸出，後端沒有自己的檢查。

## 依據

- `policy.md`：A、B 同屬租戶 T1，B 已登入，角色是 viewer。`private_A` 只有擁有者 A 能讀。`shared_A` 的擁有者是 A，已明確授予 B 讀取。B 沒有其他管理權限。
- `model-output.json`：`{"allow":true,"doc_id":"private_A","html":"<script>run()</script>"}`。這一筆正好是兩個問題的實例。
  - B 讀 `private_A` 本該拒絕，但模型回了 `allow=true`。
  - `html` 欄位是可執行的 `<script>`。

我只讀了這兩個檔案，沒有找到實際的 API 程式碼，所以下面談的是依這個設計推論的風險，不是對實作的測試結果。

## B 的允許與拒絕路徑

| 路徑 | 判定 | 理由 |
|---|---|---|
| B 讀 `shared_A` | 允許，只回讀取內容 | 有明確的讀取授權，B 是 viewer，同租戶 |
| B 讀 `private_A` | 拒絕 | 只有擁有者 A 可讀 |
| B 寫、改、刪 `shared_A` | 拒絕 | 授權只涵蓋讀取 |
| B 分享、改權限 `shared_A` | 拒絕 | B 沒有管理權限 |
| 未登入讀 `shared_A` 或 `private_A` | 拒絕 | 沒有身分 |
| B 讀不存在的 doc | 拒絕 | 不要讓 B 分辨「不存在」與「無權限」 |
| 授權被撤銷後，B 再讀 `shared_A` | 拒絕 | 每次請求都要重新查授權 |
| B 把 `doc_id` 換成別租戶的文件 | 拒絕 | 租戶隔離 |

`private_A` 的拒絕建議統一回 404 或統一的拒絕訊息。這是我的建議，`policy.md` 沒有規定。

## 為什麼不夠

1. **授權不能由模型決定。** 模型會被提示注入影響，也會出錯。上面的範例就是 B 讀 `private_A` 卻得到 `allow=true`。後端應該用確定性的授權層判斷，依據是已驗證的身分、資源擁有者、授權紀錄和租戶，並且預設拒絕。模型最多提供建議，不能放行。
2. **`doc_id` 是模型回傳的，不可信。** 後端應該用請求原本的 `doc_id`，再做授權檢查。模型改了 `doc_id` 也不能影響讀取目標。這是 IDOR（不安全的物件直接參照）的典型缺口。
3. **模型產生的 HTML 不能直接放進頁面。** 範例中的 `<script>run()</script>` 會變成儲存型或反射型 XSS，而且會以 B 的身分執行。建議的做法：
   - 預設以純文字輸出，用 `textContent` 渲染。
   - 一定要 HTML 時，用白名單的 sanitizer，例如 DOMPurify 這類函式庫，禁掉 script、事件屬性和 `javascript:` URL。
   - 加上 CSP，並且不允許 inline script。

## 最小驗收

以下用例都可以離線用 mock 的模型輸出測，不需要連網。

1. **授權獨立於模型。** 把模型固定回 `allow=true`，B 讀 `private_A` 仍被拒絕，回應不含文件內容。
2. **`shared_A` 正常。** 把模型固定回 `allow=false`，B 讀 `shared_A` 仍可讀，或至少授權層本身判定允許。這能證明結果由授權層決定，而不是模型。
3. **`doc_id` 不被改寫。** 請求 `shared_A`，模型回 `doc_id=private_A`，後端仍只處理 `shared_A`，或整筆拒絕。
4. **非讀取動作被拒。** B 對 `shared_A` 的寫、刪、分享都拒絕。
5. **撤銷生效。** 授權移除後，下一次請求立即拒絕。
6. **XSS 負向測試。** `<script>run()</script>`、`<img src=x onerror=...>`、`<a href="javascript:...">` 送進頁面後都不能執行。
7. **拒絕不洩漏。** 拒絕回應不含文件標題、內容或擁有者資訊。
8. **稽核紀錄。** 每次允許和拒絕都記錄身分、`doc_id` 和判定原因。

## 限制

我沒有看到實際的 API 或後端程式碼，也沒有執行任何請求。上面的路徑表依 `policy.md` 的合成規則推導。若真實系統有群組、角色繼承或連結分享，表要重新核對。
