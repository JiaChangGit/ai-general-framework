**結論:不夠。** 授權和輸出兩處都不能照你說的做。

## 判斷依據

`policy.md` 的規則是:A、B 同屬租戶 T1,B 已登入,角色是 viewer。`private_A` 只允許擁有者 A。`shared_A` 的擁有者是 A,並已明確授予 B 讀取。B 沒有其他管理權限。

`model-output.json` 的內容是 `{"allow":true,"doc_id":"private_A","html":"<script>run()</script>"}`。這筆輸出剛好踩到兩個問題:

- **授權:** 模型對 B 讀 `private_A` 回了 `allow=true`,但規則要求拒絕。後端若照做,B 就讀到 A 的私有文件。
- **輸出:** `html` 欄位是 `<script>run()</script>`。直接放進頁面,就會在使用者的瀏覽器執行,也就是 XSS。

兩者的共同原因是,模型輸出是不可信資料。授權要由後端的可信程式判定,輸出要依用途驗證和編碼後才能進頁面。這也是 `workflow.md` 對 API 變更的要求。

## 應允許與拒絕的路徑

後端自己查資料,依下表判斷。`allow` 欄位不能當依據。

| 請求者 | 文件 | 結果 | 理由 |
|---|---|---|---|
| B | `shared_A` 讀取 | 允許 | 擁有者 A 已明確授予 B 讀取 |
| B | `private_A` 讀取 | 拒絕 | 只有擁有者 A 可讀 |
| A | `private_A` 讀取 | 允許 | A 是擁有者 |
| A | `shared_A` 讀取 | 允許 | A 是擁有者 |
| B | `shared_A` 寫入、刪除、改分享設定 | 拒絕 | 只授予讀取,B 是 viewer |
| B | `private_A` 寫入、刪除、改分享設定 | 拒絕 | B 不是擁有者,也沒有管理權限 |
| 未登入 | 任一文件 | 拒絕 | 沒有身分 |
| 其他租戶的使用者 | 任一文件 | 拒絕 | 租戶不同(來自租戶隔離的一般要求,`policy.md` 沒有寫) |
| B | 不存在的 `doc_id` | 拒絕 | 與 `private_A` 回傳同樣的錯誤,避免洩漏文件是否存在 |

前三列之外,後面幾列是我依規則推導的。`policy.md` 沒有寫寫入、刪除和跨租戶,實作前要和產品確認。

## 建議的處理方式

1. 後端用登入身分、租戶、文件擁有者和分享紀錄,自行決定能不能讀,然後才讀檔。
2. 模型回傳的 `allow` 只能當參考。它說 `true` 而規則說拒絕時,以規則為準。它說 `false` 時,也不能因此放寬任何限制。
3. `doc_id` 要在後端對照白名單或資料庫紀錄,不能直接拿來組檔案路徑,以免被塞入 `../` 之類的路徑。
4. 模型產生的 HTML 不直接進頁面。
   - 預設當純文字,用輸出編碼處理。
   - 若一定要顯示格式,就用白名單 sanitizer,只留必要標籤,並移除 script 和事件屬性。
   - 另加 CSP 作為第二層防護。

## 最小驗收

1. **授權:** 以 B 的身分各請求一次 `shared_A` 和 `private_A`。`shared_A` 應回傳內容,`private_A` 應被拒絕且沒有內容。
2. **偽造的 allow:** 讓模型(或測試替身)對 B 讀 `private_A` 回 `allow=true`。後端仍須拒絕,回應中不能有任何 `private_A` 的內容。
3. **路徑穿越:** `doc_id` 含 `../`、絕對路徑或編碼過的路徑時,必須被拒絕。
4. **輸出:** 以 `<script>run()</script>` 當模型輸出,頁面上不能執行 `run()`。它應該顯示成純文字,或被移除。再加一筆帶 `onerror` 屬性的 `<img>` 測試。
5. **錯誤一致性:** 拒絕和不存在的回應要一致,日誌要記下被拒絕的原因。
