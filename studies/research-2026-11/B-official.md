## A. Agent Skills format and triggering

### 1. Current SKILL.md specification

**1a. Open standard (agentskills.io)** - https://agentskills.io/specification [READ]

| Field | Required | Constraint (verbatim where quoted) |
|---|---|---|
| `name` | Yes | "Max 64 characters. Lowercase letters, numbers, and hyphens only. Must not start or end with a hyphen." Also: no consecutive hyphens; "Must match the parent directory name" |
| `description` | Yes | "Max 1024 characters. Non-empty. Describes what the skill does and when to use it." |
| `license` | No | name or bundled file |
| `compatibility` | No | "Max 500 characters" |
| `metadata` | No | map string->string |
| `allowed-tools` | No | "Space-separated string of pre-approved tools... (Experimental)". Example: `Bash(git:*) Bash(jq:*) Read` |

- Directories: `scripts/` ("executable code"), `references/` ("documentation... agents can read when needed"), `assets/` ("templates, resources"). All optional.
- Progressive disclosure: "1. Metadata (~100 tokens): name and description loaded at startup for all skills. 2. Instructions (< 5000 tokens recommended): the full SKILL.md body. 3. Resources (as needed)."
- "Keep your main SKILL.md under 500 lines. Move detailed reference material to separate files." "Keep file references one level deep from SKILL.md. Avoid deeply nested reference chains."
- Validator: `skills-ref validate ./my-skill`.

**1b. Anthropic platform best practices** - https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices [READ]
- Same limits (name <=64, description <=1,024, "Cannot contain XML tags"). Additionally name "Cannot contain reserved words: `anthropic`, `claude`" (this is NOT in the open spec).
- "Keep the SKILL.md body under 500 lines for optimal performance."
- "For reference files longer than 100 lines, include a table of contents at the top."
- Keep references one level deep because "Claude might use commands such as `head -100` to preview content rather than reading entire files".
- Scripts: "Solve, don't defer" (handle errors in the script); "Prefer scripts for deterministic operations"; "Make execution intent clear: 'Run `analyze_form.py`' (execute) vs 'See `analyze_form.py` for the algorithm' (read as reference)". Pre-made scripts "Save tokens (no need to include code in context)" and are "more reliable than generated code".
- "Always write in third person. The description is injected into the system prompt".
- Use forward slashes; avoid time-sensitive info; use `ServerName:tool_name` for MCP tool references.
- Gerund naming suggested (`processing-pdfs`).

**1c. Claude Code's own frontmatter** - https://code.claude.com/docs/en/skills [READ; page was 119k chars, I read it all across two fetches except portions the extractor omitted]
Claude Code is a superset and differs from the open spec:
- "All fields are optional. Only `description` is recommended." `name` is optional ("Defaults to the directory name") - this disagrees with the open spec, which makes name required.
- Fields: `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context` (`fork`), `agent`, `background`, `hooks`, `paths`, `shell`, `metadata`, `license`, `compatibility`.
- "Claude Code ignores a field it doesn't recognize without reporting an error" (so a cross-host SKILL.md with extra keys is safe in Claude Code).
- "Keep `SKILL.md` under 500 lines."
- Recommended layout: `SKILL.md` (required), `reference.md`, `examples.md`, `scripts/helper.py` ("utility script - executed, not loaded"). Scripts are referenced via `${CLAUDE_SKILL_DIR}` (also `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`).
- Locations: enterprise (managed), `~/.claude/skills/`, project `.claude/skills/`, nested `<subdir>/.claude/skills/` (loads only after Claude touches a file in that subdir), plugin `skills/`. Override by name: managed > user > project (https://code.claude.com/docs/en/features-overview [READ]).
- Live reload: "Claude Code watches skill directories for file changes... within the current session, without a restart"; a newly created top-level skills dir needs `/reload-skills`.
- Folder name `synced` (any case) is reserved; `anthropic-skills` prefix does not load outside a plugin.
- Frontmatter must start on line 1: "Claude Code reads the frontmatter only when the opening `---` is the file's first line." Malformed YAML: "the skill still loads with no fields set" (so `/name` works but description matching does not).
- Post-compaction: "the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens."

### 2. Description writing, trigger failures, listing budget, control fields

**Official guidance on descriptions**
- Open spec: "Should describe both what the skill does and when to use it. Should include specific keywords". Good vs poor: "Helps with PDFs." is the poor example. [READ]
- Platform: "Be specific and include key terms... Claude uses it to choose the right Skill from potentially 100+ available Skills." [READ]
- Claude Code: "Put the key use case first: the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing". [READ]
- Codex: "Write concise descriptions and front-load the key use case and trigger words." [READ] (https://learn.chatgpt.com/docs/build-skills)

**Documented reasons a skill fails to trigger** (https://code.claude.com/docs/en/skills, "Troubleshooting") [READ]
1. Description lacks keywords users would say.
2. Skill not in the listing (`What skills are available?`).
3. Frontmatter malformed / `---` not on line 1 -> "Claude can't match against your `description`". Run `--debug`; `claude plugin validate .claude/skills` finds unparsable frontmatter (v2.1.233+).
4. Name contains refused characters (zero-width, `<`, `>`) -> doesn't load.
5. `paths` set and the files Claude touches are outside the current working directory (e.g. sibling worktree).
6. `disable-model-invocation: true` -> "Claude can't invoke the skill on its own."
7. **Listing budget overflow** (below).
8. After compaction only the start of an invoked skill survives: "put the most important instructions near the top of `SKILL.md`."
- Skill ignored later in a session: "Claude Code adds the skill's content to the conversation when the skill is invoked and doesn't re-read the file on later turns." For rules that must always hold: "move the rule into a hook".
- Angle brackets in description are displayed as `&lt;`/`&gt;`; use square brackets.

**Listing / character budget** (https://code.claude.com/docs/en/skills, "Skill descriptions are cut short") [READ]
- "The listing always contains every skill name, but if you have many skills, Claude Code drops some descriptions to fit the listing's character budget, which removes the keywords Claude needs to match your request. The budget scales at 1% of the model's context window. When the listing overflows, Claude Code drops descriptions starting with the skills you invoke least."
- Per-entry cap: 1,536 characters for `description` + `when_to_use`; configurable via `skillListingMaxDescChars`.
- Raise the shared budget: `skillListingBudgetFraction` (e.g. `0.02` = 2%) or env `SLASH_COMMAND_TOOL_CHAR_BUDGET` (fixed char count).
- Reduce: `skillOverrides` per skill = `"on" | "name-only" | "user-invocable-only" | "off"`; `disableBundledSkills`.
- Diagnostics: `/doctor` (listing cost estimate), `/skill-doctor` ("see what each of your skills costs and how often it gets used"; v2.1.252+; prints text in `-p`), `/context` Skills row (reports post-budget size since v2.1.196), `--debug` warning.
- Third-party search snippets mention an "8,000-character fallback" for the budget; the official page I read only states the 1% rule [SEARCH-ONLY for the 8,000 figure]. Codex documents "2% of the context window, or 8,000 characters when the window size is unknown" [READ].

**Invocation-control fields** [READ, same page + features-overview]
- `disable-model-invocation: true`: "prevent Claude from automatically loading this skill... Use for workflows you want to trigger manually". Context effect: "Set `disable-model-invocation: true` in a skill's frontmatter to keep its description out of Claude's context" (features-overview). "Use `disable-model-invocation: true` for skills with side effects."
- `user-invocable: false`: hidden from `/` menu; Claude-only.
- `allowed-tools`: "Tools Claude can use without asking permission during the turn that invokes this skill. The grant clears when you send your next message." (A grant, not a restriction; use `disallowed-tools` to remove tools.)
- `context: fork` (+ `agent:`): run in a forked subagent. A skill with a `model:` different from the session is a model switch for that turn and breaks the prompt cache (prompt-caching page).
- `paths`: glob patterns; "Claude loads the skill automatically only when working with files matching the patterns."
- `hooks` in frontmatter: registered when the skill is invoked and kept "for the rest of the session".
- `shell`, `${CLAUDE_SKILL_DIR}` substitutions, `` !`cmd` `` injection (disable with `disableSkillShellExecution`).

### 3. Evaluating skills (late 2026)

- **skill-creator plugin** (https://code.claude.com/docs/en/skills, "Run evals with skill-creator") [READ]: stores `evals/evals.json` in the skill dir; "spawns a subagent per test case so each run starts with a clean context, and records token count and duration"; grades assertions to `grading.json`; aggregates with-skill vs without-skill pass rate/time/tokens into `benchmark.json`; "runs a blind A/B between two versions"; "Description tuning: generates should-trigger and should-not-trigger prompts, measures the hit rate, and proposes description edits"; HTML review viewer. Eval file format documented at https://agentskills.io/skill-creation/evaluating-skills (link only; not fetched).
- **`claude plugin eval`** (https://code.claude.com/docs/en/plugin-evals) [READ, 63 KB page, I read the relevant sections via grep]: "runs your plugin against a suite of test cases and scores the results. Each case is a realistic prompt plus one or more graders." Layout `evals/<case>/prompt.md` + `graders/*.md`. Grader types (six; four are deterministic: `regex`, `tool_used`, `tool_order`, `file_exists`; plus `llm` and `baseline`). Trigger test = `type: tool_used`, `tool: Skill`, `input_match: '"skill"\s*:\s*"(?:[\w-]+:)?your-skill-name"'`. Runs a no-plugin baseline arm and reports `Delta`; `tool_used: Skill` graders are `scored: false` in the two-arm comparison. Judge model default = background-task model; `--judge-model sonnet` to override. Cost: "roughly cases x runs agent runs with the plugin and the same number again for the no-plugin baseline". Mocks for MCP tools under `evals/mocks/`. `--scaffold` runs a case script outside the sandbox. "neither tool reads the other's case files" (skill-creator vs plugin eval formats are incompatible). The skills page notes it works for skills "in a plugin", so a bare `~/.claude/skills` skill must be wrapped (a "skills-directory plugin" is mentioned) [partially READ].
- **`/skill-doctor`**: usage/cost report, flags never-invoked skills (above). It is a usage report, not a quality eval.
- **`claude plugin validate`**: syntax/schema check only.
- Platform guidance (best-practices page) [READ]: "Create evaluations BEFORE writing extensive documentation"; "At least three evaluations created"; "Tested with Haiku, Sonnet, and Opus". And the note: "There is not currently a built-in way to run these evaluations" (that sentence is stale relative to Claude Code's tools above; the platform page was not updated - a documentation disagreement).
- Anthropic engineering skills post: "Start with evaluation: Run agents on representative tasks, find where they struggle, and build skills incrementally" (https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) [READ].

**Where the same SKILL.md works and where not**
- Works everywhere: `name` + `description` + body + `scripts/ references/ assets/` (this is the agentskills.io core; Codex page says it builds on that standard). Three hosts (Codex, Gemini, OpenCode) converge on `.agents/skills/`. Claude Code's docs list only `.claude/skills` (symlink `.claude/skills` -> `.agents/skills` is a possible bridge [FROM-MEMORY, UNVERIFIED: not documented; Claude Code does follow symlinks for rules, but I did not verify for skills]).
- Claude-only or host-specific: `when_to_use`, `disable-model-invocation` (also honored by OpenCode), `user-invocable`, `context: fork`, `paths`, `hooks`, `${CLAUDE_SKILL_DIR}`, `` !`cmd` `` injection, `allowed-tools` semantics (spec marks it experimental; Claude Code treats it as a per-turn grant). Codex-only: `agents/openai.yaml`. Unknown keys are ignored by Claude Code; OpenCode accepts `license/compatibility` without interpreting; Gemini behavior for unknown keys not verified.
- Windows/path hazard: platform page says use forward slashes.
- Name constraint divergence: Claude platform bans names containing `anthropic`/`claude`; Claude Code reserves `synced`; OpenCode derives ID from path, not from `name`.

### 6. MCP in 2026

- **Tool search in Claude Code** (https://code.claude.com/docs/en/mcp) [READ, section extracted from the saved page]: "Tool search keeps MCP context usage low by deferring tool definitions until Claude needs them. Only tool names and server instructions load at session start". On by default for Opus 4 / Sonnet 4 / Haiku 4.5 and later; `ENABLE_TOOL_SEARCH`: unset/`true` = defer all; `auto` = load upfront while definitions total <10% of context, `auto:N` custom; `false` = all upfront. Server authors: tool descriptions and server instructions are capped (4,096 chars upfront; 16,384 when loaded via tool search; `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`); "put critical details near the start"; `_meta["anthropic/alwaysLoad"]` forces a tool upfront; `anthropic/maxResultSizeChars` raises per-tool result persist threshold (default 50,000 chars, hard ceiling 500,000).
- Output limits: "Claude Code displays a warning when MCP tool output exceeds 10,000 tokens and limits output to 25,000 tokens by default" (`MAX_MCP_OUTPUT_TOKENS`).
- What does a definition cost: Anthropic measured ~55K tokens for 58 tools (advanced-tool-use post above). Per-tool cost in your own session: `/context all` ("see how many tokens each loaded MCP tool uses").
- **Cache interaction**: with tool search on, "Claude Code keeps the tool list from the conversation's first request for the whole conversation, so a server connecting or disconnecting mid-session doesn't disturb anything already cached"; without it, adding/removing a server invalidates the cache (prompt-caching page [READ]).
- **Spec revisions**: 2025-11-25 [READ changelog https://modelcontextprotocol.io/specification/2025-11-25/changelog]: OIDC discovery, incremental scope consent, URL-mode elicitation, sampling with tools, Client ID Metadata Documents, experimental Tasks, JSON Schema 2020-12 default, tool name guidance. **2026-07-28** [READ official blog https://blog.modelcontextprotocol.io/posts/2026-07-28/, via extractor]: "MCP is transforming from a bidirectional stateful protocol into a request/response stateless protocol"; `initialize` handshake and `Mcp-Session-Id` retired; `server/discover`; Multi Round-Trip Requests replace server-initiated elicitation/sampling/roots; `Mcp-Method`/`Mcp-Name` headers; `ttlMs`/`cacheScope` on list results; Tasks move to extension `io.modelcontextprotocol/tasks`; "Roots, Sampling, and Logging are deprecated" (kept >=12 months); legacy HTTP+SSE deprecated; Dynamic Client Registration deprecated in favor of CIMD; `iss` validation (RFC 9207). The draft security page also states DCR is "deprecated as of protocol version `2026-07-28`" [READ]. I did not open the spec's own 2026-07-28 changelog page; whether a newer revision exists after July 2026 was not confirmed (search snippets say none found) [SEARCH-ONLY].
- **Security guidance** (https://modelcontextprotocol.io/specification/draft/basic/security_best_practices) [READ]: confused deputy (per-client consent, exact redirect-URI match, `__Host-` cookies), "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server" (token passthrough forbidden), SSRF (block private/link-local ranges, egress proxy), state-handle hijacking, local server compromise ("MUST implement proper consent mechanisms prior to executing commands"; sandbox, `stdio` transport), OAuth URL scheme validation, mix-up attacks, scope minimization. **The MCP spec page does not discuss prompt injection or "tool poisoning" as such** (I searched the page; the terms do not appear). [READ]
- Claude Code MCP security: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." (mcp page [READ]); "We encourage either writing your own MCP servers or using MCP servers from providers that you trust... Anthropic... does not security-audit or manage any MCP server." (https://code.claude.com/docs/en/security [READ]). Project `.mcp.json` servers need approval in interactive sessions but "A `-p` session shows neither prompt."
- No tool-poisoning-specific official guidance found; treat as a gap.

## C. Context, cost, sessions, models

### 7. Claude Code instruction loading

Source: https://code.claude.com/docs/en/memory [READ via saved 54 KB output, targeted greps + preview] and https://code.claude.com/docs/en/context-window [READ] and features-overview [READ].
- "Each Claude Code session begins with a fresh context window." Two mechanisms: CLAUDE.md and auto memory. "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead."
- **Size**: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Warning at startup and in `/status` when over; "Claude Code skips a file over 4 MiB"; a combined-size warning also exists. `/doctor` offers trim proposals; `/doctor prompt-audit` audits CLAUDE.md/AGENTS.md/rules/skills/commands/subagents/output styles. Content rule: "Keep it to facts Claude should hold in every session... If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule." costs.md: "Aim to keep CLAUDE.md under 200 lines by including only essentials."
- **Imports**: `@path/to/import`, relative to the containing file, "maximum depth of four hops"; imports inside code spans/fences are not expanded; imports are loaded eagerly, so they do NOT save context. External (outside cwd) imports in project files require a one-time approval dialog.
- **Rules**: `.claude/rules/*.md` recursive; rules with `paths:` frontmatter load only when matching files are touched; user-level `~/.claude/rules/`; symlinks supported (external symlink targets need approval).
- **Nested CLAUDE.md** in subdirectories load on demand "once Claude reads, writes, or edits another file in that subdirectory"; per-file size limit applies there ("Claude receives only the start of it").
- `<!-- block comments -->` in CLAUDE.md are stripped before injection (free maintainer notes). `claudeMdExcludes` skips files by glob.
- **AGENTS.md**: read directly (v2.1.277+) or via `@AGENTS.md` in CLAUDE.md; "Claude Code skips an `AGENTS.md` it has already loaded, so one that your `CLAUDE.md` imports... isn't read twice". A CLAUDE.md that merely says "read AGENTS.md" in words works only if Claude chooses to open it. Windows: use the import, not a symlink.
- **Auto memory**: `MEMORY.md` "first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; topic files are on demand; per-repository, shared across worktrees; main conversation's auto memory is not loaded into subagents (except forks); subagents can have their own memory.
- **Always in context** (context-window page): system prompt, auto memory, environment info, MCP tool names, skill descriptions, `~/.claude/CLAUDE.md`, project CLAUDE.md, unscoped rules, output style. Illustrative numbers there: system prompt 4,200, skill descriptions 450, project CLAUDE.md 1,800 tokens ("counts are illustrative").
- **Subagents**: fresh context with own system prompt; CLAUDE.md and git status load unless built-in Explore/Plan or `omitClaudeMd`; preloaded skills via `skills:` field; only a summary returns. A fork inherits the parent conversation.
- **Compaction** ("What survives compaction", context-window page [READ]): system prompt/output style survive; project-root CLAUDE.md and unscoped rules "Re-injected from disk"; auto memory re-injected; skill descriptions rebuilt (v2.1.304+); invoked skill bodies "capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first"; up to five recently touched files re-read (files >5,000 tokens come back as a path reference); **path-scoped rules and nested CLAUDE.md "are summarized away"** - "If a rule must persist across compaction, drop the `paths:` frontmatter or move it to the project-root CLAUDE.md"; hook-added context is summarized; `SessionStart` hooks matching source `compact` re-run; background tasks keep running. `/compact <focus>`, `/rewind` -> "Summarize from here", `/autocompact 500k`, `/clear`; compaction can be customised from CLAUDE.md ("# Compact instructions" section, costs.md).
- `/context` gives "a live breakdown by category with optimization suggestions"; `/memory` edits loaded files. 1M-context variants exist (`[1m]`).

### 8. Prompt caching, model switching, handoff files

- **Mechanism** (https://code.claude.com/docs/en/prompt-caching [READ in full]): "The API caches by matching the start of each request, called the prefix... The match is exact, so a change anywhere in the prefix recomputes everything after it." Layers: system prompt + tool definitions -> project context (CLAUDE.md, auto memory, unscoped rules) -> conversation.
- **TTL**: five-minute and one-hour. Defaults: Claude subscription within plan usage: main conversation one hour; everything else (subagents, workflows, compaction, forks, teammates) five minutes. API key/cloud provider: five minutes for everything (set `promptCacheTtl: "1h"` or `CLAUDE_CODE_PROMPT_CACHE_TTL`; subagents `subagentPromptCacheTtl`; requires v2.1.242+). "Once you go over your plan's usage limit and Claude Code draws on usage credits... Claude Code drops the main conversation to the five-minute TTL". Cache refresh is free on each hit.
- **Prices** (https://platform.claude.com/docs/en/build-with-claude/prompt-caching [READ first 100k chars]): "Cache write tokens with a 5-minute TTL are 1.25 times the base input tokens price. ... 1-hour TTL are 2 times... Cache read tokens are 0.1 times" (0.05x for Opus 5.5 / Sonnet 5.5; 0.025x for Fable/Mythos 5.1/5.2). "By default, the cache has a 5-minute lifetime." Minimum cacheable prompt 512 tokens for the 5.x models, 1,024-4,096 for older.
- **Invalidates the cache** (Claude Code page): switching model ("Each model has its own cache. Switching with `/model` means the next request reads the entire conversation history with no cache hits"); changing effort on most models (not on Fable 5.1+, Opus 5.5, Sonnet 5.5, Haiku 5.5 with API key/subscription); fast mode on/off; adding/removing an MCP server when tool search is not deferring; removing a tool via a bare-tool deny rule when tool search is off; compaction (conversation layer rebuilds; the compaction call itself is cheap only while the cache is warm and "costs the most when you resume an old session"); accumulating images (oldest batch dropped); upgrading Claude Code; skill/command with a different `model:` frontmatter; `opusplan` toggling plan mode; automatic model fallback.
- **Keeps the cache**: editing repo files, editing CLAUDE.md mid-session ("Claude Code reads these files at session start and holds them in memory. To reload them, run `/clear` or `/compact`, or restart"), permission-mode changes, output-style switch (v2.1.251+), invoking skills/commands, `/recap`, `/rewind`, spawning subagents, enabling plugin skills/hooks/agents. API-level invalidation table (platform page): tool definition changes invalidate everything; web-search/citations toggles hit system+; thinking-parameter changes invalidate messages.
- **Model switch advice**: `/model` "asks you to confirm the switch only while the cache is still warm"; guidance "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks between tasks." A `PreModelSwitch` hook can require/skip confirmation. Settings page: `model` edits mid-session via `/model` only.
- **Scope**: cache is "effectively scoped to one machine and directory" (system prompt embeds memory paths, cwd). Parallel sessions in the same directory can share prefix.
- **Resuming**: "When you resume a session, Claude Code sends the whole conversation again, and the request reads from the cache whatever part of its prefix is unchanged and still within the cache lifetime." The resumed conversation keeps its original system prompt until compaction. `/status`/`/usage` show `Prompt cache (main)` hit ratio and likely cause of last miss (v2.1.251/260+).
- **Official handoff / progress-file guidance**
  - Harness post https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents [READ via extractor]: initializer agent + coding agent; `claude-progress.txt` "A log of what earlier agents did, used with git history to help a fresh context window get oriented"; feature list as JSON ("JSON was chosen because models are less likely to corrupt it than Markdown"; agents may only flip `passes`; "It is unacceptable to remove or edit tests"); descriptive git commits; `init.sh`; "Split work into one feature per session"; "Require clean, mergeable code at the end of each session"; "Start each session by reviewing progress notes, git history, and the feature list."
  - Prompting best practices https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices [READ via saved output, "Workflows across multiple context windows"]: use a different first-window prompt to set up tests/scripts; "Have the model write tests in a structured format (for example, `tests.json`)"; "Set up convenience tools (for example, `init.sh`)"; "**Choose between starting fresh and compacting:** ... Claude's latest models are extremely effective at discovering state from the local filesystem" with a prescriptive start prompt ("Review progress.txt, tests.json, and the git logs."); "Use structured formats for state data"; "Use git for state tracking".
  - Context-engineering post: structured note-taking to NOTES.md outside the window [READ].
  - Claude Code best practices https://code.claude.com/docs/en/best-practices [READ via grep of saved output]: `/goal` sets a condition "a separate model checks against the conversation after every turn"; `Stop` hook "sends Claude back to work if the script exits with code 2" (capped at eight consecutive blocks; override env `CLAUDE_CODE_STOP_H...` truncated in my extract); "Give Claude a check to run".
  - `/rename` before `/clear`, then `/resume` (costs page) is the in-product session-handoff mechanism.

### 9. Usage limits and in-flight tasks

- https://code.claude.com/docs/en/interactive-mode "Wait for a usage limit to reset" [READ]: "When a claude.ai usage limit stops Claude mid-task, Claude Code waits in the open session and continues the task on its own after the limit resets. Automatic continue is on by default in interactive sessions signed in with a claude.ai subscription. Requires Claude Code v2.1.234 or later." At reset: "Claude Code prompts Claude to pick the task up where it stopped. It doesn't resend your last message." Permissions still prompted ("the task can stop on a prompt while you're away"). "After three automatic continuations, automatic continue stops"; `/rate-limit-options`; Esc cancels. The wait ends (no continuation) if you exit Claude Code ("the wait doesn't restart when you resume the session"), clear/rewind, `/resume` another session, `/login` another account, move the session, or the reset is >24 h away. Managed control: `autoContinueAtUsageLimit`.
- costs.md [READ]: "'You've hit your session limit'... a seat-based usage window on a subscription plan, shared across all models, so the developer can't restore access by switching models with `/model`." Model-specific messages ("Opus limit"/"Sonnet limit") can be bypassed by switching to another family. `/usage-credits` to continue now. Switching models during the wait triggers a re-check. Windows: "a rolling five-hour window and a weekly window" (Teams/Enterprise; shared with chat and Cowork).
- Cheap checkpoint/resume (all [READ]): `-p` + `--output-format json` returns `session_id`; `claude -p "..." --resume <id>` or `--continue`; `--resume` accepts an absolute path to a `.jsonl` transcript. SIGTERM leaves the in-progress turn unfinished and unrecorded; "To have Claude Code continue the interrupted turn on resume instead, set `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`" (headless page). Resume after the cache TTL means a full uncached re-read (prompt-caching page), so `/clear` + a handoff file is cheaper than resuming a huge stale session; "`/clear` costs nothing" (costs.md); `/compact` of a large cold context "is itself a large request".
- A `-p` cap exists: `--max-budget-usd` and `--max-turns` (named in headless/github-actions pages [READ]; exact semantics not fully read).

## D. Boundaries

### 10. Hooks, permissions, sandbox, security, Codex

**Hooks** (https://code.claude.com/docs/en/hooks [READ first 100k of 294k chars; decision-control table truncated]; best-practices page [READ])
- **33 events**: SessionStart, Setup, UserPromptSubmit, UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, MessageDisplay, SubagentStart, SubagentStop, TaskCreated, TaskCompleted, Stop, StopFailure, TeammateIdle, InstructionsLoaded, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, Elicitation, ElicitationResult, SessionEnd.
- Handler types: `command`, `http`, `prompt`, `agent` (experimental), `mcp_tool`. Common fields: `type`, `if` (permission-rule syntax), `timeout`, `statusMessage`, `once`. Only `command`/`http` are deterministic: "A `prompt` or `agent` hook asks another model to decide, so it isn't deterministic either."
- **Exit codes**: "0 (success)... 2 (blocking error): On events that can block, the action is stopped. The stderr text is the reason... Any other code (non-blocking error): The action proceeds"; "Exit 1 is non-blocking unless the hook sets `onFailure: "block"`. ... If your hook is meant to enforce a policy, use `exit 2`."
- **Can block**: PreToolUse, UserPromptSubmit, UserPromptExpansion, Stop, SubagentStop, TeammateIdle, TaskCreated, TaskCompleted, ConfigChange (not policy_settings), PostToolBatch, PreCompact, PreModelSwitch, Elicitation, ElicitationResult, WorktreeCreate/Remove. **Cannot block**: PermissionRequest (use decision object), PostToolUse/PostToolUseFailure ("the tool already ran"), PermissionDenied, StopFailure, Notification, Setup, InstructionsLoaded, MessageDisplay, SessionStart, SubagentStart, SessionEnd, CwdChanged, FileChanged, PostCompact, PostModelSwitch, DirectoryAdded.
- JSON output: `hookSpecificOutput.permissionDecision` allow/deny/ask/defer for PreToolUse (requires `hookEventName`); PreToolUse can rewrite input (`updatedInput`, used in the costs page example).
- Config locations: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed, plugin `hooks/hooks.json`, skill/subagent frontmatter. "Hook entries merge across levels rather than replacing each other." `disableAllHooks` cannot disable managed hooks. "Hooks and other `.claude/settings.json` keys load from the current working directory's `.claude/` folder with no parent-directory fallback" (permissions page).
- Interaction with permissions: "A hook that exits with code 2 stops the tool call before permission rules are evaluated"; conversely "PreToolUse hook decisions don't bypass permission rules... a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned 'allow'." (permissions page [READ]).
- Guidance: "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook." "Keep the enforced set small... If you ever find yourself at forty of them, most are probably preferences". Under `--bare` hooks (even via `--settings`) do not run.
- Sandbox does not cover hooks: "Claude's file tools, MCP servers, and hooks run outside it."

**Permissions** (https://code.claude.com/docs/en/permissions [READ via saved 90 KB output, targeted greps; page not read end to end])
- Order: "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order." An allow cannot carve an exception out of a deny.
- Syntax: `Tool` or `Tool(specifier)`; `Bash(npm run *)`, trailing ` *` also matches the bare command; `Bash(ls *)` vs `Bash(ls*)` (space matters); `:*` suffix equivalent; bare tool name as deny "removes the tool from Claude's context entirely"; `Read(./.env)`, gitignore-style paths, `Read(!path)` carve-outs only within the same settings source; `WebFetch(domain:...)`.
- **Known gaps / bypasses documented by Anthropic**: "A Bash rule matches the command text Claude writes... It doesn't match the same program invoked in a different form, so a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." `Bash(curl *)` does not match `/usr/bin/curl` or `sh -c 'curl ...'`; `Bash(git push *)` does not match `git -C . push`; `Bash(rm *)` does not match `/bin/rm`/`bash -c 'rm...'`. "Bash permission patterns that try to constrain command arguments are fragile." Wrapper stripping is a fixed list (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`; bare `xargs`); `npx`, `docker exec`, `direnv exec`, `devbox run`, `mise exec` are not stripped so `Bash(devbox run *)` matches anything after `run`. Compound commands split on `&& || ; | |& &` and newlines; deny/ask applies if any subcommand matches; env-var prefixes stripped only for known-safe vars on allow rules, any var for deny/ask. Read/Edit deny rules "don't apply to a command that reads files without naming them, such as `grep -r pattern .`" (truncated line; I read the first clause only). Output redirects and `tee` are checked against Edit rules. Symlinks: allow needs both paths to match, deny matches either. The doc's own recommendation: "For filesystem and network enforcement that doesn't depend on the command text, use sandboxing. To inspect the full command text with your own logic before it runs, use a PreToolUse hook."
- **Settings precedence** (https://code.claude.com/docs/en/settings [READ in full]): "managed settings, command line, project local, shared project, user" (highest first). Lists such as `permissions.allow` merge across scopes (deny/ask also combine; rule order above decides). `permissions.defaultMode` `auto`/`bypassPermissions` are ignored from project/local files. Project `allow` rules and `additionalDirectories` wait for workspace trust; `deny`/`ask` apply immediately. Settings reload live (permissions, hooks), except some keys (e.g. `permissions.blockReadsOutsideWorkingDirectories` removal needs restart). `.claude/settings.json` is read from the session's primary working directory (not parents); `.claude/settings.local.json` is placed at the git-repo root (v2.1.211+). `~/.claude.json` holds MCP configs and trust state. Security-restrictive keys (e.g. `permissions.blockWritesOutsideWorkingDirectories`, `denyInsteadOfPrompting`) are honored from any scope even over managed.
- Modes: Manual, auto (classifier; default starting mode for interactive terminal/VS Code), `acceptEdits`, `dontAsk`, plan, `bypassPermissions` (disable with `permissions.disableBypassPermissionsMode`/`disableAutoMode`). Best practices: "your 'never' rules belong in deny rules or hooks" not in auto mode's judgment.
- **Sandbox** (https://code.claude.com/docs/en/sandboxing [READ first 100k of 111k]): "a boundary that the operating system enforces around the shell commands Claude runs"; off by default (`/sandbox` or `sandbox.enabled`); macOS Seatbelt, Linux/WSL2 bubblewrap, "Native Windows: not supported"; filesystem write limited to cwd + temp, but "Reads are allowed across most of the machine by default, including credential files like `~/.ssh`, unless you restrict them"; network via proxy with `allowedDomains` (starts empty; hostname only, no TLS inspection); "Claude's file tools, MCP servers, and hooks run outside it"; `allowUnsandboxedCommands: false` to prevent `dangerouslyDisableSandbox` retries; protected paths (settings, hooks, `.git/hooks`, shell startup files). Permissions and sandbox are complementary: "Permission rules and sandboxing control different things."
- **Security page** (https://code.claude.com/docs/en/security [READ]): prompt-injection safeguards are permission system, network-command approval, fail-closed matching, command-injection detection, WebFetch via a separate model call; untrusted-content practices: "Avoid piping untrusted content directly to Claude... Use virtual machines (VMs) to run scripts and make tool calls". "While these protections significantly reduce risk, no system is completely immune to all attacks." `ConfigChange` hooks can audit settings edits. "A `-p` session shows neither prompt [workspace trust nor MCP approval]" - so a malicious repo's hooks/.mcp.json run in headless mode unless `--bare` is used.
- **Codex** (https://learn.chatgpt.com/docs/agent-approvals-security [READ via extractor]): sandbox modes `read-only`, `workspace-write`, `danger-full-access`; approval policies `on-request`, `never`, `granular`; `untrusted` "retired"; "the agent runs with network access turned off"; version-controlled folders default to `Auto` (workspace-write + on-request), non-VCS folders `read-only`; under workspace-write `.git`, `.codex`, `.agents`, `.aws` inside writable roots are read-only; `--yolo` = `--dangerously-bypass-approvals-and-sandbox`. Note: Codex protects `.agents/` (where cross-host skills would live) from agent writes.

### 11. CI: GitHub Actions and headless

- Headless page https://code.claude.com/docs/en/headless [READ in full]: `claude -p`; "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." `--bare` skips hooks, skills, plugins, MCP servers, auto memory, CLAUDE.md; needs `ANTHROPIC_API_KEY` or `apiKeyHelper` (no OAuth/keychain); context passed explicitly via `--append-system-prompt[-file]`, `--settings`, `--mcp-config`, `--agents`, `--plugin-dir`. Hooks passed with `--settings` do not run under `--bare`. Without `--bare`, `-p` "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted."
- Permission handling: `--allowedTools "Bash(git diff *),..."`; in Manual-mode `-p` "a call that needs approval is denied unless something approves it" (`PermissionRequest` hook or `--permission-prompt-tool`); v2.1.302+ `-p` starts in Manual mode when nothing sets a mode; `--permission-mode dontAsk` "useful for locked-down CI runs"; `--permission-prompts none` (v2.1.259+) or `permissions.denyInsteadOfPrompting`; auto mode drops a bare `Bash` allow entry.
- Outputs: `--output-format text|json|stream-json`; JSON includes `total_cost_usd`, `session_id`, `permission_denials`; `--json-schema` -> `structured_output`; `system/init` has `plugin_errors`/`mcp_server_errors` ("a CI gate can fail on a non-empty array"). Exit code 0 on success, non-zero on failure. Piped stdin capped at 10 MB. `--max-budget-usd` stops remaining background work when hit. SIGTERM gives exit 143 and an unfinished turn.
- GitHub Actions page https://code.claude.com/docs/en/github-actions [READ in full]: action `anthropics/claude-code-action@v1`; secrets `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` (via `claude setup-token`; for shared org secrets use an API key because the OAuth token is tied to one person); OIDC/workload identity federation (`id-token: write`) to avoid long-lived secrets; "Grant the workflow only the permissions it needs"; who can trigger: write access required, bots rejected unless in `allowed_bots`; fork PRs get no secrets; guardrails listed under "Manage costs": "Keep your `CLAUDE.md` concise, since Claude reads it on every run", `--max-turns` in `claude_args`, "workflow-level timeouts", "GitHub's concurrency controls"; automation mode with a plain-text prompt has no shell access "until you grant the tools the prompt needs, with `--allowedTools`"; a skill invocation gets its `allowed-tools`; `/skill-name` prompt runs repo skills after `actions/checkout`. Gotcha: commits made with default `GITHUB_TOKEN` do not trigger CI; scheduled workflows run only from default branch and are disabled after 60 days of inactivity in public repos. The GitHub App has a broad permission set (Actions r/w, Workflows r/w, Administration read, etc.); a custom app with Contents/Issues/Pull requests is the least-privilege alternative. Security doc for the action: https://github.com/anthropics/claude-code-action/blob/main/docs/security.md (linked, not fetched).
