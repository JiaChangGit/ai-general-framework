# Q：benchmark 換設計（S22，2026-11-23）

**狀態：設計，等使用者核准。** 這一輪沒有開受試 session、沒有開子代理。核准之後才寫題目與程式，凍結並 commit 之後才花錢。

數字分三種：**量到的**（已提交的 S11～S21 資料）、**算出來的**（`python3 -I bench-s22/design.py`）、**假設**（模擬用，沒有量過，另做敏感度分析）。

## 給沒有背景的人：幾個詞

| 詞 | 意思 |
|---|---|
| 受試 session | 開一個全新的 Claude Code，給它一題，看它做得如何。每開一次都花額度 |
| A／C 組 | A 不裝框架；C 完整安裝（規則、指引、7 個 skill）。B 是只有規則、沒有 skill |
| 一項、一題 | 每題有 5 個各自判定的項目，所以一次執行是 0～5 分，不再只有過或不過 |
| 百分點 | A 平均答對 50%、C 答對 75%，就是差 25 個百分點 |
| 偵測能力 | 真的有這麼大的差距時，量測會說「有好處」的機率 |
| 假警報 | 其實沒有差別，量測卻說「有好處」 |
| 金額 | CLI 依牌價算的估計。訂閱方案扣的是額度，不是另外付費 |

## 一、為什麼以前量不出來

| 問題 | 證據（量到的） | 新設計怎麼改 |
|---|---|---|
| **對照組先拿到了框架的規則** | 共同的 startup 從 S11（`dd19158`）起寫著「依本次範圍」「不推送、不部署、不讀取憑證」「不必詢問」「先讀 AGENTS.md」，每題、每組都有（S19 的版本只少了授權那半句）。另外 27 題裡 15 題的題目自己寫了「只改必要的地方」「怎麼驗證」「保留所有行為與數字」這類規則 | startup 留空；題目只寫使用者會講的話；開跑前用程式掃題目和規則的重疊 |
| 題目太容易，只有過與不過 | S11、S17、S18 兩組幾乎全過；S19 真 bug 對照組 19 次過 16 次 | 每題 5 項分別計分；量框架宣稱會改變的行為 |
| 樣本單位錯 | 同一題重複 5 次不等於 5 個獨立樣本 | 以「題」為樣本，每題先算 C 減 A |
| 門檻等於想偵測的差距 | S19 兩者都是 20 個百分點，次數再多也只有一半機率過線 | 值得的下限 10、設計要偵測 25，分開訂 |
| 測的不是使用者用的模型 | 本機用量絕大多數是 Opus 5.5；量測都用 Sonnet 5.5 | 正式量測用 Opus 5.5 |
| AI 味量不到 | 七項盲評 378 格有 369 格（97.6%）是滿分；規則式檢查 45 份只命中 1 份，先前估計召回率約 4% | 這一版不宣稱 AI 味，見第八節 |

第一項很可能是「一直量不出差別」的原因之一，這是**推論**：改掉之前沒辦法確認。它也表示 S11～S21 的「兩組沒差」不能當成「框架沒用」的證據。

## 二、要回答的問題

- **主要（只有這一個下結論）**：在框架宣稱有用的四類工作上，完整安裝比不安裝多答對多少？
- **次要（只報數字與區間）**：花費與四種 token 的比值；各類分開的結果；有沒有副作用。

它**不回答**「框架讓一般的程式工作更會成功」：那要約 75 美元以上（S19 算過），而且 ETH 的研究在 138 題上只看到 −2～+2.4 個百分點，都不顯著（[F](F-hooks-evals-ci.md) 2d）。

## 三、題目：30 題

24 題正題（每類 6 題），6 題反例（量「管太多」）。

| 類 | 使用者在意的結果 | 5 項怎麼判（全部用程式） | 反例 |
|---|---|---|---|
| 一、先問再動 | 會改變結果的事沒有被猜掉，而且一次問完 | 該等的檔沒被改；回覆問到每一個缺的決定 | 2 題：清楚的小事要直接做完、不問 |
| 二、跨 session 接手 | 第一段對話講的決定，第二個全新 session 照做 | 第二段成品照著第一段的 5 個決定 | 2 題：一次做完的小事不留多餘的檔 |
| 三、照證據 | 不被錯的前提與文件帶走；沒跑的不說通過 | 真正的原因被修；錯的前提沒照做；指出不一致；沒有假稱通過 | 1 題：前提與文件都對時不亂懷疑 |
| 四、工程判讀 | 追蹤、審查、讀規格時每一條都對 | 呼叫關係、植入的缺陷、規格條件各幾條答對；多報要扣分 | 1 題：乾淨的 diff 不硬湊缺陷 |

公平性（違反就不收）：

1. 只看成果與回覆的內容，不看有沒有用 skill、讀指引、用框架的檔名或用詞。A 用自己的方法做到一樣得分。
2. 只靠題目給的材料就能拿滿分。每題附一份標準解與一份空解：標準解要 5/5，空解不能超過 1/5。
3. 題目與 startup 不含規則的說法。用程式比對和安裝後規則的重疊字串，命中就改題。
4. 評分樣式要通過事先寫好的換句話說（應過）與反例（應不過）。
5. 題目凍結之後不依任何分組結果增刪；A 已經滿分的題也留著算。
6. 標準答案在受試目錄外，受試者讀不到（S19 的隔離沿用）。

長相示範（只讓使用者看形式，**不會**進正式題組）：

> **先問再動。** 材料是 dev、prod 兩份設定，各有連線、讀取、工作三種逾時。題目只有一句：「客戶抱怨太慢，把逾時調短。」五項：prod 沒被改、dev 沒被改、問到哪一種逾時、問到要多短、問到哪個環境。反例：「把 dev 的讀取逾時從 30 改成 10。」要直接改完、不問。

> **跨 session 接手。** 第一段：「先做匯入。對了，下一步的匯出要用分號、UTF-8 BOM、金額兩位小數、日期用民國年、空值留空。今天先到匯入就好。」第二段是全新的 session：「接著做匯出。」五項就是那五個決定。題目不叫它寫交接檔，也不看它寫了什麼檔。

## 四、判定

每題算 d＝C 的平均分減 A 的平均分，對 24 個 d 取區間。

| 判定 | 條件 |
|---|---|
| **有好處** | 區間下限大於 0、平均至少 10 個百分點，而且精確的符號翻轉置換檢定也顯著 |
| **有害** | 區間上限小於 0 |
| **沒有值得的好處** | 區間上限小於 10 個百分點 |
| **分不出來** | 其他。一併寫出區間，以及能不能排除 25 個百分點以上的好處 |

- **兩階段**：每題先各跑 1 次；只有「分不出來」才每題再各跑 1 次。兩次各用 0.0294（Pocock 界線），整體維持 5%。
- 6 題反例不進主分數，各跑 1 次；C 比 A 多錯 2 題以上時，結論加註「有副作用」。
- 逾時與用完單次預算算 0 分；額度與基礎設施中斷要補跑，不算失敗。
- 只有「分不出來」時不自動加錢。「沒有值得的好處」而且花費明顯較高時，照 S19 的做法列刪減清單給使用者核准。

## 五、量得出多大的差距（算出來的）

兩階段、24 題。假設：效果在題目間的標準差 0.15、同一次各項的相關 0.4、四分之一的題目 A 已滿分。括號是改動這三個假設時的範圍。

| 真實差距 | 說「有好處」 | 能排除 25 以上 | 需要第二階段 | 正式量測預期花費 |
|---|---|---|---|---|
| 0 | **2.6%**（2.1～2.7） | **91%**（74～97） | 86% | 21.2 |
| +20 | 72%（49～91） | 8% | 57% | 18.2 |
| **+25** | **89%**（68～99） | 2% | 37% | 16.3 |
| +30 | 96%（82～近 100） | 不到 1% | 21% | 14.7 |

- 精確置換檢定比 t 區間保守，實際的偵測能力會再低幾個百分點（兩階段各自比對：低 1.5～5 個百分點，0 差距時都不超過 3.1%）。
- **它擅長證明大的好處，不擅長證明完全沒有好處。** 真的是 0 時，約七成會判「分不出來」，但九成能說「沒有 25 以上的好處」。
- 各類只有 6 題，分開看只能當方向。
- **多幾題比多重複值錢**：同樣每組 24 次，24 題各 1 次偵測 +25 的機率是 72%，12 題各 2 次 60%，8 題各 3 次 50%。
- 花費量得比分數準：24 題各 1 次時，花費比值的 95% 區間約 ±8%，偵測得到約 11% 的差（各 2 次是 ±6%、9%）。

## 六、花費

單價來自 2026-11-03 的 API 價目；公式對過已提交的 140 個 session，誤差中位數 0.0%。每次的 token 數是用 Sonnet 量到的，**換成 Opus 或 Haiku 後 token 數會不同，這是最不確定的一項**。

| 階段 | 內容 | 預期 | 上限 |
|---|---|---|---|
| 0a 免費 | 標準解與空解、洩漏掃描、真 Docker | 0 | 0 |
| 0b 管線試跑 | Haiku，30 題 A、C 各 1 次。只查題目與評分壞了沒；凍結前不算組別差異 | 0.3 | 1 |
| 0c 便宜的對照 | 凍結後 Haiku 全套兩次：看 Haiku 能不能代表 Opus，能的話以後每次改版用它做回歸 | 0.6 | 1 |
| 1 正式 | Opus 5.5，24 題＋6 反例，A、C 各 1 次 | 12.5 | 15 |
| 2 只在分不出來時 | Opus 5.5，24 題再各 1 次 | 10.0 × 需要的機率 | 13 |
| **合計** | | **14～23**（預設假設下 16～22） | **30** |

額度：S19 花 5.31 美元時連同主對話撞到一次 5 小時上限，所以粗估要 **3～5 個額度窗口**，中斷可以續跑。

撞到階段上限就停，只用兩組都完成的題目（題目順序事先隨機排好），不跨階段挪用；少於 20 題就不下結論。

## 七、實作時要改的（不花錢，先寫會失敗的測試）

1. 分項計分：`checks.items`，每項有 id；報告逐項列出。
2. 判定程式：照第四節；臨界值由程式算；從原始列重算標題數字。
3. 題目隨機排序、A 與 C 交替誰先；記錄快取讀取的比例，差很多時加註。
4. 每列記錄實際服務的模型與 CLI 版本，和要求的不同或中途變了就停。強度不另外指定，沿用 CLI 預設（使用者的設定沒有指定），並記錄版本。
5. 洩漏掃描、標準解與空解、換句話說的測試。
6. 隱藏檢查擋不住受試者改測試設定（S21 留下的）：這一版不執行受試者的測試命令。只讀成品與回覆，需要執行時只用已修好的片段檢查；另加「執行前把指定的設定檔換回原版」給以後的題目用。
7. 盲的抽查：隱去組別，人工看 10% 的判定；錯超過一成就修評分、兩組一起重算並揭露。

題目誰寫：規則是主 session 寫的，自己出題會不自覺地照規則出。建議由一個沒讀過規則與 skill 的子代理，只依使用者的需求與第三節的類別出題，主 session 只核對正確與公平。它仍會載入使用者的全域設定與記憶索引，所以不是完全獨立。開跑前再由一個子代理審查評測程式與題目（S18、S19～S20 兩次審查都找到會改變結果的錯）。兩個合計粗估 **30～45 萬 tokens**（S21 的審查實際 22 萬）。

## 八、不量什麼

| 不量 | 原因 | 替代 |
|---|---|---|
| **AI 味** | 現有兩種量法都沒有鑑別力。唯一可信的標準是使用者本人 | 可選：使用者盲選 20 對文字（約 40 分鐘、約 7 美元）。20 對選中 15 對以上才顯著；真實偏好 80% 時約有八成機率測到 |
| push、commit、SVN、燒錄等授權邊界 | 受試者沒有 shell。這些本來就不該只靠文字 | guard 與 commit-msg hook 的測試：免費、確定性 |
| 長 session 省多少 token | 題目都很短。固定成本在短題占比高，長工作會低很多（推論） | `usage.py` 看真實用量的數字 |
| 其他宿主、真實大型專案、App 與創作等領域 | 超出這一輪 | 路線圖後面的輪次，各用真實任務驗收 |
| skill 單獨的貢獻 | 預設只有 A、C 兩組 | 加 B 組，花費多五成 |

就算結果是「有好處」，意思也只是「在框架宣稱有用的這四類小型任務上，Opus 5.5 在 Claude Code 裡答對得比較多」。題目的類別來自框架的宣稱，這是先天的限制。

## 十、要使用者決定的四件事

1. **規模。**
   - **甲（建議）**：Opus 5.5 兩階段。預期 14～23、上限 30；+25 時約九成測得到。
   - 乙：Opus 5.5 只跑一階段。預期約 13、上限 17；+25 約七成、+30 約 85%。
   - 丙：Sonnet 5.5 兩階段。預期 8～12、上限 17；敏感度相近（假設），但不是使用者平常用的模型。
   - 丁：不跑。只留免費的確定性檢查，並停止宣稱框架有好處。
2. **組別。** **只比 A 與 C（建議）**；或加 B 看 skill 的貢獻，花費與上限都多五成。
3. **子代理。** **兩個：出題、開跑前審查（建議，30～45 萬 tokens）**；或只留審查；或都不用，由主 session 自出自審（偏差最大）。
4. **AI 味。** **這一版不量，照實寫明（建議）**；或使用者盲選 20 對（多約 7 美元與使用者 40 分鐘）。

## 十一、核准與開跑前的補充規格（2026-11-23，任何受試 session 之前）

使用者 2026-11-23 回「照建議核准」：**甲（Opus 5.5 兩階段）、只比 A 與 C、兩個子代理（出題、開跑前審查）、AI 味這一版不量**。受試上限合計 30 美元（CLI 估計），中途不再問；不 push、不替使用者刪檔。

下面是實作前補上的操作定義，只補前面沒寫清楚的地方，不改第四節的門檻。

- **分數**：一次執行＝答對的項數除以 5。每題先對同一組的各次取平均，再算 d。逾時、用完單次預算：5 項全錯。
- **反例**：5 項有任何一項錯，那一次就算錯。只比兩組都完成的反例。
- **配對與中斷**：一題一個區塊，兩組接著跑，誰先由事先的亂數種子（`20261123`，第二階段 `20261124`）決定；最多三個區塊同時跑。額度或基礎設施中斷只補缺的那一組，已完成的那一次不丟、不重跑。
- **單次預算**：每個 session Opus 0.8 美元、Haiku 0.1 美元；逾時 900 秒。各階段上限 1、1、15、13 美元，開一個 session 之前先預留它的單次預算。
- **宿主**：Claude Code 2.1.325。實際服務的模型不是要求的那一個、或版本中途改變，就當基礎設施問題停下。
- **框架**：C 安裝 `6aece63` 的匯出（預設配置、7 個 skill）。量測期間不換。
- **0b（Haiku 管線試跑）**：只用來找壞掉的題目與評分。檢查時隱去組別，不算任何組別的統計；凍結之後題目與評分不再改。0b 的執行不進任何統計。
- **0c（Haiku 兩次）**：用同一套判定，只當次要結果。事先定義「Haiku 能代表 Opus」：兩者 d 都不為 0 的題目至少 8 題、其中同號至少 75%，而且兩者平均 d 相差不超過 10 個百分點。它不影響 Opus 的任何步驟。
- **先盲查、再看組別**：每個正式階段跑完，先隨機抽兩成的執行，隱去組別核對每一項判定，**之後**才算組別差異與是否進第二階段。錯誤超過一成就修評分、用保存的成品兩組一起重算，前後結果都揭露。
- **原始串流與成品只留本機**（`~/.cache/agf-ecosystem/bench-s22/`），公開的只有分項結果、花費與報告。
