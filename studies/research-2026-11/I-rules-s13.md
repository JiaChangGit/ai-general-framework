# 縮短常駐規則（S13，2026-11-18）

S12 量到框架每個 session 一開始多讀約 2,640 tokens，其中規則約 1,920，是最大的一塊（[H 報告](H-measurement-s12.md)）。這一輪把規則縮短，量兩件事：固定成本少了多少；縮短之後，上一輪的 8 個任務有沒有變差。

原始資料：[measurement-s13/](measurement-s13/)。

## 改了什麼

| | 改之前 | 改之後 |
|---|---|---|
| `templates/project-rules.md` | 1,413 字 | 1,073 字（少 24%） |
| 安裝到專案的 `.agf/managed/project-rules.md`（含安裝工具附加的工具模式說明） | 約 1,670 字 | 約 1,330 字 |

每一條規則都留著它的指示。刪掉的是兩種：模型不用提醒也會做的說明（例如「先找出相關的範圍再讀」、「把目的、因果和例子接起來」），以及 skill 描述和指引裡已經寫了的清單（例如 `agf` 子命令的名單）。

初稿交給另一個模型（claude-sonnet-5-5）逐句對照新舊版。它指出 5 處刪得太多，都補回來了：

- 「連之後才會用到的決定也一起問」
- 「把查到的寫進問題」
- 「專案規則和使用者的指示衝突時先指出」
- 「確認暫存的只有這次的檔案」
- 「偏好用 `agf profile show --root <專案目錄>` 查」

附加的工具模式說明原本寫死 `python3`，Windows 常常只有 `python` 或 `py -3`，所以改成列出這三種。

## 固定成本

「只回覆 OK」的 session，比較第一次呼叫模型時讀進去的 token 數。

量測時遇到一個干擾：使用者環境裡有一個 MCP 伺服器在中途連上，之後的 session 看到的工具從 23 個變成 31 個，第一次呼叫因此多了約 1,730 tokens。所以下表只拿工具數相同的兩次互相比較：

| 比較 | 工具數 | 數字（tokens） | 規則或框架的成本 |
|---|---|---|---|
| 只有規則（新）對 S12 的對照組 | 23 | 20,974 − 19,363 | 規則 1,611 |
| 只有規則（新）對同時跑的對照組 | 31 | 22,704 − 21,095 | 規則 1,609 |
| S12：只有規則（舊）對對照組 | 23 | 21,283 − 19,363 | 規則 1,920 |
| 全部（新）對 S12 的對照組 | 23 | 21,684 − 19,363 | 框架 2,321 |
| S12：全部（舊）對對照組 | 23 | 22,003 − 19,363 | 框架 2,640 |

- **規則少了約 310 tokens**（1,920 → 約 1,610，少 16%）。兩種比法得到的數字只差 2 tokens。
- **框架的固定成本少了約 320 tokens**（2,640 → 2,321，少 12%）。
- 換成花費，這個最小的 session 從 0.0518 美元降到 0.0506 美元，大約少 2%。

[probe-report.md](measurement-s13/probe-report.md) 的中位數把 23 個和 31 個工具的 session 混在一起算，所以那張表的數字不要直接拿來比；上表才是同條件的比較。量測工具從這一輪起會記下每個 session 看到的工具數（`tools_listed`），之後的報告看得出這種干擾。

## 有沒有變差

S11 的 8 個任務，框架組用新規則各跑 1 次，hook 的設定和 S11 相同：

| 任務 | S11 框架組（通過，花費中位數） | S13（通過，花費） |
|---|---|---|
| fix-admitter | 2/2，0.087 | 通過，0.091 |
| fix-pager | 2/2，0.081 | 通過，0.082 |
| trace-customer-id | 2/2，0.070 | 通過，0.067 |
| review-withdraw | 1/1，0.073 | 通過，0.075 |
| rewrite-zh | 1/1，0.108 | 通過，0.109 |
| simple-edit | 1/1，0.071 | 通過，0.068 |
| continue-after-limit | 2/2，0.180 | 通過，0.169 |
| switch-model | 2/2，0.092 | 通過，0.087 |
| 合計 | 0.763 | 0.749 |

- 8 個全部通過；花費合計少 2%，這個差距在雜訊範圍內。
- 行為沒有看得出的改變：`fix-admitter` 一樣叫用 `debug-root-cause`，`review-withdraw` 一樣叫用 `review-change`，`rewrite-zh` 一樣去讀寫作指引。
- 這 8 個 session 都是 23 個工具，沒有受到上面那個干擾。

## 結論

1. **規則縮短 24%，安全，但省得不多**：每個 session 少約 310 tokens，花費約少 2%。
2. **固定成本仍占框架多花的錢裡相當大的一部分。** 推算（沒有另外量）：S11 每個 session，框架組的 cache creation 平均多 4,672 tokens，其中約 2,640 是第一次呼叫就寫進快取的固定 context；cache read 多的 7,107 tokens，大半是之後每一輪重讀這段固定 context。其餘來自行為：讀 skill 全文、讀指引、多讀檔案、比較長的輸出。例如 `rewrite-zh` 去讀寫作指引，cache creation 就多了約 7,300 tokens。
3. **要再省得多，只修字不夠。** 規則剩約 1,610 tokens、skill 描述約 720，加起來約占第一次呼叫的一成。下一步有兩條路：把大部分規則移到需要時才讀的指引，常駐的只留幾句；或從行為下手，例如把寫作指引拆成常用的短版和完整版。兩條都要再量一次品質，才知道會不會變差。

## 限制

- 回歸只跑 1 次，和 S11 的 1～2 次比較；只看得出有沒有明顯變差。
- 只量了固定成本與 8 個任務。新規則對「一開始問完問題」這類行為的影響，這些任務測不到。
- 量測途中使用者環境多了一個 MCP 伺服器；已排除受影響的那幾次。

## 花費

固定成本探測 0.31 美元（含補跑），8 個任務 0.75 美元，合計約 1.06 美元。
