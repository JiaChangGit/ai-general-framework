## PART 1: Hooks

### Common stdin fields [READ]
`session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort`, `hook_event_name`, plus `agent_id`/`agent_type` when relevant. `model` is not always present.

### Universal JSON output [READ]
- `continue` (default true): false stops Claude. `stopReason` shown when continue=false. `systemMessage`: warning shown to user. `suppressOutput`: "Has no effect." `terminalSequence`: allowlisted OSC/BEL, ignored in `-p` and the Agent SDK.
- Exit 0: stdout JSON parsed; plain-text stdout is added as context for SessionStart / UserPromptSubmit / PostModelSwitch. Exit 2: blocking where the event can block, stderr is the reason; elsewhere stderr is shown to the user only.
- Caps: `additionalContext`, `systemMessage`, `initialUserMessage` and plain stdout are capped at 10,000 chars each; over the cap the output goes to a file with a 2,000-char preview. PreCompact stdout is exempt from this cap (but "Keep that stdout under 10,000 characters per hook" and longer output is cut with a marker, per the PreCompact section).

### Decisive quotes [READ]
- Stop loop guard: "The `stop_hook_active` field is `true` when Claude Code is already continuing as a result of a stop hook. Check this value or process the transcript to avoid blocking on a condition that will never resolve."
- Cap: "Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. The count of consecutive continuations resets each time Claude calls a tool. To raise the cap, set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`."
- Stop `additionalContext` shares the same guards: "namely the `stop_hook_active` input and the 8-consecutive-continuation cap".
- StopFailure `error` values: `rate_limit`, `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `invalid_request`, `model_not_found`, `server_error` (HTTP 529 maps here), `max_output_tokens`, `cloud_credential_error` (v2.1.267+), `unknown`. Matcher syntax for it: letters, digits, `_`, `|` only.
- PreCompact: "When a PreCompact hook exits 0 and doesn't block, Claude Code uses its stdout as instructions for the compaction summary." Blocking auto-compaction: if proactive, "Claude Code skips it and the conversation continues uncompacted"; if triggered to recover from an API context-limit error, "the underlying error surfaces and the current request fails."
- PostCompact: use it "to react to the new compacted state, for example to log the generated summary or update external state."
- PostModelSwitch: "It can't block, because the model has already changed."

### Unresolved on StopFailure / usage limits [READ + gap]
The StopFailure table has `rate_limit` but the docs I read do not state that a claude.ai *subscription usage-limit* ("You've hit your session limit") maps to `rate_limit` rather than another value, nor whether StopFailure fires while automatic-continue is waiting. The usage-limit error page (code.claude.com/docs/en/errors) was not read. Treat the mapping as unverified; log `error` and `error_details` raw and test empirically.
Note the interplay with built-in auto-continue (Part 4): Claude Code already waits and continues on its own in interactive sessions, so a StopFailure hook should not try to re-prompt.

### once / if / statusMessage / timeout [READ]
- `once`: "honored only in skill frontmatter. Removes the hook after its first successful run. Failures, exit 2, and timeouts leave it in place. Ignored in settings files and agent frontmatter." So `once` in a settings.json or hook template does nothing; implement once-per-session with a marker file keyed by `session_id`.
- `if`: permission-rule syntax such as `"Bash(git *)"`. "Evaluated only on PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest, and PermissionDenied. On other events a hook with `if` set never runs." Exactly one rule (no `&&`/`||`). Do NOT put `if` on SessionStart/Stop/etc.
- `statusMessage`: "Custom spinner message displayed while the hook runs."
- `timeout` (seconds): defaults 600 command/http/mcp_tool, 30 prompt, 60 agent; lowered to 30 for command/http/mcp_tool on UserPromptSubmit, PreModelSwitch, PostModelSwitch (10 on MessageDisplay). Not enforced for `async: true` command hooks. SessionEnd shares a 1.5s budget unless raised.
- Up to 12 prompt/agent hooks run concurrently per event; an identical handler defined in several settings files runs once.

### Environment variables [READ]
`CLAUDE_PROJECT_DIR` ("the project root where the session started"; stays fixed when Claude enters a worktree), `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_PLUGIN_OPTION_<KEY>`, `CLAUDE_EFFORT`, `CLAUDE_CODE_REMOTE` ("true" in web environments), `CLAUDE_CODE_BRIDGE_SESSION_ID`. "There is no `$CLAUDE_MODEL`. Use `from_model`/`to_model`." On PowerShell, bare `$CLAUDE_PROJECT_DIR` resolves to `$null` (docs warn).

### Headless `-p` and `--bare` [READ]
- Without `--bare`, `-p` runs project `.claude/settings.json` hooks and `.mcp.json` servers "even in a folder you've never trusted" (no trust dialog). SessionStart/Setup hook events stream as `hook_started/hook_progress/hook_response` with `--output-format stream-json --verbose`. `initialUserMessage` is a `-p`-only SessionStart output. `terminalSequence` ignored. Project subagent hooks need workspace trust, "A `-p` session doesn't count as accepting it."
- `--bare`: "skipping auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory, and CLAUDE.md". Critically: "Hooks still don't run in bare mode when you pass them with `--settings`, or in the `hooks/hooks.json` ... of a plugin you load with a flag. Don't use bare mode for a run that needs them." It also drops system reminders (no skill list shown), background tasks, and requires `ANTHROPIC_API_KEY` (or apiKeyHelper / cloud creds), never OAuth/keychain. Skills in an `--add-dir` directory's `.claude/skills/` still load. It sets `CLAUDE_CODE_SIMPLE`. Docs: "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." => Hook-dependent tests must not use `--bare`; for isolation use `--settings '{"disableAllHooks": true}'` or the plugin-eval sandbox.
- Whether Stop/PreCompact/SessionEnd hooks fire in `-p`: SessionEnd does (SIGTERM section: "Claude Code then runs SessionEnd hooks"); SessionStart does. For Stop in `-p` the docs I read give no explicit statement [NOT FOUND]; test it.

### Design implications
1. Stop hook: always check `stop_hook_active`; prefer `additionalContext` over `decision:block` for guidance; remember the cap is 8 and resets on any tool call; raise only via `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`.
2. PreCompact stdout = compaction instructions: a template can inject "preserve X" text without any JSON. PostCompact gets `compact_summary` for checkpointing to a file.
3. SessionStart `source=compact|resume|clear` lets one hook re-inject handoff/checkpoint context; on resume use `prompt_cache_likely_expired` and `estimated_cache_write_usd` to warn about cold-cache cost (v2.1.251+).
4. PreModelSwitch gives a ready-made cost warning (`estimated_cache_write_usd`); `ask` only works interactively; in `-p` it is a refusal.
5. No hook sees `$CLAUDE_MODEL`; read the stdin fields.

## PART 2: Measuring whether a framework/skill set helps, and at what cost

### 2a. `claude plugin eval` [READ: code.claude.com/docs/en/plugin-evals]
- Requires Claude Code v2.1.269+; git 2.31+. Separate from skill-creator: "neither tool reads the other's case files" (skill-creator uses `evals/evals.json`).
- Layout: `evals/<case>/prompt.md` (frontmatter: `max_turns`, `timeout_seconds`, `model`, `tags`, `allowed_tools`, `env`, `runs`; body = prompt), optional `case.yaml` (context.* fixtures, history_file, scaffold_script, plugins), `graders/<name>.md`. A case without a grader fails to load.
- Grader types (6): `regex` (JS regex; targets incl. final reply, files, mock_calls; `match: not_contains|count:N`), `tool_used` (`tool`, `input_match`, `min`, `max`; use min 0/max 0 for "must not fire"), `tool_order`, `file_exists`, `llm` ("A judge model votes PASS on the rubric in at least two of three votes"), `baseline` (judge compares with a reference transcript). "There are no custom-code graders." Free (no model call): regex/tool_used/tool_order/file_exists. Judge default = background-task model; `--judge-model` to choose.
- Scoring: "each case runs three times by default"; run score = fraction of graders passing (weights allowed); case score = mean of runs; passes when >= `--threshold` (default 1.0).
- Baseline: "a case's runs are repeated with no plugin loaded, and you get two scores, WITH and W/OUT. Their difference, Δ". Trap handled by the tool: `tool_used: Skill` graders (and mock-call graders on plugin-declared servers) are marked `scored:false` in two-arm runs ("A check like 'the skill was invoked' can never pass without the plugin"), shown as indicators only; override with `arm: both|with-only`. `--ablation none` = one arm, halves cost.
- Trigger tests: no separate format. A trigger test is a normal case with a `tool_used: Skill` grader (`input_match: '"skill"\s*:\s*"(?:[\w-]+:)?your-skill-name"'`); a negative control is the same with `min: 0, max: 0, arm: both`. `claude plugin eval init` proposes "prompts that should and shouldn't trigger the plugin". Docs: "the usual cause ... Δ near zero with the case's `tool_used: Skill` grader failing, ... the skill's description doesn't trigger on the prompt's phrasing."
- Isolation: each run = fresh temp home/cwd/config, `claude -p` child; user settings, hooks, CLAUDE.md, MCP, other plugins, memory absent; "The case definitions are hidden from the agent" (no answer-key leak via the eval dir). Tools: only read-only set unless `--allow-tools`; Bash needs OS sandbox.
- Cost: "Every eval run and every judge grader is a real model call". Model-call count ~ cases x runs x 2 arms + 3 judge calls per llm/baseline grader per run. Reported `costUsd` is a list-price estimate. `--max-cost-usd` is checked before each run starts; spend can pass it; exit 2 and `partial:true`. Tokens by type are not mentioned in what I read [NOT FOUND]; `aggregate-result.json` has `costUsd`, `durationSeconds`, `claudeVersion`, per-run grader results, `aggregates.overallScore/meanDelta`, `cases[].aggregates.delta`.
- CI recipe (verbatim from docs): `claude plugin eval . --trust-plugin --json results.json --threshold 0.8 --model claude-sonnet-5 --judge-model claude-haiku-4-5 --no-publish --max-cost-usd 20`. Exit codes: 0 pass, 1 below threshold/load error/API error run, 2 partial (cost ceiling or credential rejected), 130 interrupted, 143 terminated. "The with-minus-without delta is reported but never changes the exit code." "Pin both models so scores are comparable over time", "leave partial: true documents ... out of any trend you chart". `init` needs a TTY; in CI use `claude plugin eval init --bare <name>`.
- Judge hygiene (docs): grade long output with `regex` not `llm`; one grader on the result plus one on the steps (`tool_used`/`tool_order`); "If a case's tool_used: Skill grader passes but Δ is negative, suspect the judge before the plugin. A small judge model can mark a correct answer wrong because it's formatted differently".
- Limit for this framework: it evaluates a *plugin* (needs plugin.json or a skills-directory plugin). A hooks+CLI+guides framework is only partly covered; CLAUDE.md-style context is not loaded in runs ("Nothing personal or project-level loads"). So it measures skills, not AGENTS.md/CLAUDE.md effects.

### 2b. agentskills.io guidance [READ]
Evaluating output quality (agentskills.io/skill-creation/evaluating-skills):
- Case = prompt + expected_output + optional files in `evals/evals.json` (`skill_name`, `evals[]` with `id`, `prompt`, `expected_output`, `files`, later `assertions[]`). "Start with 2-3 test cases." Assertions added after seeing a first run; "Reserve assertions for things that can be checked objectively."
- Run each case with skill and without (or against a snapshot of the old skill), each "with a clean context". Workspace `iteration-N/eval-X/{with_skill,without_skill}/{outputs,timing.json,grading.json}` + `benchmark.json` with mean and stddev per arm and a `delta` of pass_rate, time_seconds, tokens.
- Timing: `timing.json` = `{"total_tokens", "duration_ms"}` only (no input/output/cache split); "Save these values immediately - they aren't persisted anywhere else."
- Grading: LLM for fuzzy assertions, scripts for mechanical ones ("scripts are more reliable than LLM judgment for mechanical checks"); "Require concrete evidence for a PASS. Don't give the benefit of the doubt." Blind comparison: "present both outputs to an LLM judge without revealing which came from which version".
- Analysis rules: drop assertions that pass in both arms; investigate ones that fail in both; high stddev = flaky eval or ambiguous skill. "Standard deviation is only meaningful with multiple runs per eval."
- Cost framing: "a skill that dramatically improves output quality but triples token usage is a different trade-off ... A skill that doubles token usage for a 2-point improvement might not be."
Trigger testing (agentskills.io/skill-creation/optimizing-descriptions):
- `eval_queries.json` = `[{"query": "...", "should_trigger": true|false}]`. "Aim for about 20 queries: 8-10 that should trigger and 8-10 that shouldn't." Negatives should be near-misses sharing keywords. Realistic details (paths, typos, context).
- "Run each query multiple times (3 is a reasonable starting point) and compute a trigger rate"; pass threshold 0.5 default. 20 queries x 3 = 60 invocations.
- Detection with Claude Code: `claude -p "$query" --output-format json | jq -e '... .type=="tool_use" and .name=="Skill" and .input.skill==$skill'`. Note: with `--output-format json` the exact message shape in that snippet should be re-verified against the current output (stream-json is safer; the plugin-eval tool sidesteps it).
- Train/validation split ~60/40, fixed across iterations, choose best iteration by validation pass rate, ~5 iterations; test finally on 5-10 fresh queries. Caveat: simple one-step tasks may not trigger a skill at all even with a perfect description.
- Third-party (SEARCH-ONLY): Conduction docs describe `trigger_tests` with 10+/10+ prompts and "90%+" as a community target; SkillCI (Go), aws-samples skill-eval, and a claude-plugin-sdd ADR describe path-filtered GitHub Actions (`skills/**`, `evals/**`).

### 2c. OpenAI [READ: developers.openai.com/blog/eval-skills, 2026-01-22 per search]
Eval = prompt -> captured run (`codex exec --json` JSONL) -> checks -> score. Case types: explicit, implicit, contextual, negative control (`should_trigger=false`). "a small set of 10-20 prompts is enough to surface regressions". Deterministic checks first (commands run, exit codes, files exist, command count for thrashing, clean `git status`); rubric grading by a second read-only `codex exec` with `--output-schema` returning `{overall_pass, score 0-100, checks[{id,pass,notes}]}`. Tokens from `usage.input_tokens/output_tokens` on `turn.completed`, used "to spot accidental prompt bloat". No grader model named; no repeat count (examples imply 1 run per prompt) - weaker than the Anthropic tooling on noise. Third parties on Promptfoo/Skillgrade are SEARCH-ONLY.

### 2d. ETH AGENTS.md study, arXiv 2602.11988 [READ via arxiv.org/html]
- Benchmarks: SWE-bench Lite (300 tasks, 11 Python repos, none with context files) and new CTXbench (138 instances, 12 Python repos with developer-committed AGENTS.md/CLAUDE.md; selection: root context file, Python, tests, >=400 PRs; PR must reference an issue and touch Python; agent-set-up env; >=1 test passing; LLM-written task descriptions "instructed not to leak the solution"; LLM-generated fail-to-pass tests, 25/138 manually edited to remove over-specification; ~75% coverage of modified code).
- Agents: Claude Code + Sonnet-4.5 (temp 0), Codex + GPT-5.2 / GPT-5.1 mini (temp 0), Qwen Code + Qwen3-30b-coder (temp 0.7). **One sample per agent and condition.**
- Conditions: none; LLM-generated (agent's own init command); developer-written (CTXbench only).
- Metrics: success (all tests pass), steps, "inference cost" (USD total). In the sections reviewed cost is NOT broken into input/output/cache tokens. Reasoning tokens measured for GPT models.
- Stats: Cochran-Mantel-Haenszel for resolution rate; stratified permutation tests for steps and cost; McNemar for ablations.
- Results: LLM-generated vs none: about -0.5% (SWE-bench) / -2% (CTXbench), p=0.87/0.37, steps +2.45/+3.92, cost about +20%/+23%. Developer-written vs none: about +2.4% (p=0.21); dev vs LLM p=0.038; cost up to +19%. Quote: "Surprisingly, we find that providing context files does not generally improve task success rates."
- Caveats stated: Python only; small n (SE roughly 3-4 points); contamination check by knowledge cutoff showed no consistent difference; django dominates SWE-bench; removing repo docs made LLM context files help ~2.7%; LLM-refined task descriptions raised SWE-bench accuracy ~15% (the pipeline changes difficulty).
- Takeaway for a small framework: the effect size you are trying to detect (2-4 points) is about the SE of a 138-task set; with a handful of tasks you can only detect large effects or cost/step changes.

### 2e. SkillsBench, arXiv 2602.12670 (v4) [READ via arxiv.org/html]
- 87 tasks, 8 domains, from 400 submissions by 142 contributors (22% accepted). Each: human instruction, Docker env, curated Skills, oracle solution, deterministic pytest verifier, binary reward. "explicitly avoids LLM-as-judge."
- Leakage controls: Skills must supply "expertise, not answers"; instructions never name which Skill to use; automated Skill-to-solution leakage gate rejects task-specific filenames, paths, magic numbers, verbatim oracle commands; tasks with no separation between conditions rejected; AI-text detector for instruction provenance.
- Conditions: no Skills / curated Skills / self-generated (agent writes its own with skill-creator, 3 configs only).
- Trials: three selected trials per (config, task, condition) cell; fresh pinned container each; paired deltas at (config, task); primary metric task-macro pass rate; secondary normalized gain g=(pass_skill-pass_vanilla)/(1-pass_vanilla). CIs: 95% binomial Wald, half-width 1.96*sqrt(p(1-p)/n) (Appendix G) - note this ignores pairing/clustering; normalized gain point estimate only.
- Results: 33.9% -> 50.5% (+16.6 pp); per-config +4.1 to +25.7 pp; self-generated Skills -8.1 to -11.5 pp (worse than none); focused Skills (<=3 modules) beat comprehensive (+19.0/+21.5 vs +0.7 pp); 2-3 Skills +19.0 pp vs 4+ +10.1 pp; 13 tasks had negative deltas.
- Cost: tokens go both ways (e.g. OpenHands+Opus 4.7 1.77M -> 1.09M per trial; Gemini 3.1 Pro 1.82M -> 4.02M). Quote: "cache reads can account for a material share of effective input tokens, so realized cost under cached pricing can differ substantially from standard-rate estimates." Cells with <20 usable trials suppressed. Rate-limited/unscored runs rerun, not scored as failures.
- Authors' limitations: length confound ("gains may partly reflect 'more context' rather than procedure"; length-matched controls proposed as future work); curated skills are high quality (10.1/12 vs ecosystem 6.2/12), so optimistic.

### 2f. Pitfalls checklist (sourced)
- Judge bias: MT-Bench/Chatbot Arena paper (arXiv 2306.05685) reports position, verbosity and self-enhancement bias [SEARCH-ONLY, abstract-level]. Mitigate: objective checks first, swap order / blind labels, pin judge model different from the agent model, rubric as concrete PASS/FAIL, length-normalised or length-capped comparison.
- Pass-in-both-arms: assertions passing with and without the skill measure nothing (agentskills.io; plugin-eval Δ).
- Skill-invoked graders inflate Δ unless excluded from the score (plugin-eval does this; do the same in a home-made harness).
- Answer-key leakage: case definitions hidden from agent (plugin-eval); SkillsBench leakage gate; ETH: task descriptions written "not to leak the solution". Keep graders/expected outputs outside the agent's cwd; do not put eval cases inside the repo the agent reads.
- Task-difficulty drift from LLM-polished task text (+15% in ETH study).
- Contamination: ETH split by knowledge cutoff; SkillsBench admits containerisation does not prevent memorisation.
- Caching skews cost: warm vs cold cache and 5m vs 1h TTL change dollars for identical work (prompt-caching page). In `-p`, the main conversation gets 1h TTL only on a subscription within plan usage; with an API key it is 5m (set `CLAUDE_CODE_PROMPT_CACHE_TTL` / `promptCacheTtl` to equalise arms). Report input, output, cache_read, cache_creation (5m and 1h) separately, e.g. from `--output-format json` `usage` and `usage.cache_creation.ephemeral_{5m,1h}_input_tokens`, plus `total_cost_usd` and per-model breakdown (headless page: "client-side estimates and can differ from your actual bill"). Beware `--continue/--resume` reports the conversation's cumulative total. `--bare` or isolated cwd changes the cache prefix: sessions in different dirs do not share cache ("Cache scope").
- Skill injection adds context length: a "more tokens" arm can win just by being longer; add a length-matched placebo (SkillsBench future work).
- Small n: one run per condition (ETH) cannot separate noise. plugin-eval default is 3 runs; SkillsBench 3 trials; agentskills.io says stddev is only meaningful with multiple runs. With n tasks x 3 runs and binary outcomes, use paired per-task differences (sign test / exact McNemar / bootstrap on task-level deltas) and report the count of tasks improved/flat/regressed rather than a single p-value. This synthesis is mine, not from a single source.

## PART 3: Agent checks in CI

### claude-code-action [READ: code.claude.com/docs/en/github-actions]
- Secrets: `ANTHROPIC_API_KEY` (input `anthropic_api_key`) or `CLAUDE_CODE_OAUTH_TOKEN` (input `claude_code_oauth_token`, from `claude setup-token`; tied to the generating person's subscription, so for org-shared use an API key). Also workload identity federation (`anthropic_federation_rule_id`, `anthropic_organization_id`, needs `id-token: write`), or Bedrock/Vertex/Foundry via `use_bedrock|use_vertex|use_foundry` + OIDC.
- Workflow: `uses: anthropics/claude-code-action@v1`, `actions/checkout@v6`, permissions e.g. `contents: read, pull-requests: read, issues: read, id-token: write` (`id-token: write` "required for ... default GitHub App authentication"). `prompt` present = automation mode; absent = interactive `@claude` mode. A repo skill is run with `prompt: "/skill-name"` after checkout; plugins via `plugin_marketplaces` + `plugins`.
- `claude_args` passes any CLI flag: `--max-turns`, `--model`, `--allowedTools`, `--mcp-config`, `--debug`. For plain-text prompts "Claude has no shell or GitHub API access until you grant the tools".
- Cost controls named by the docs: specific prompts, concise CLAUDE.md ("Claude reads it on every run"), `--max-turns`, workflow-level timeouts, GitHub concurrency controls. The docs do not list `--max-budget-usd` there but `claude_args` accepts any CLI argument [inference].

### Headless `claude -p` in CI [READ: headless, cli-reference]
- `--max-budget-usd`: "Stop the run once estimated spend on API calls reaches this amount (print mode only)... client-side cost estimate, which can differ from your bill. Spend from subagents counts... Spend can pass the cap, so leave headroom." Example `claude -p --max-budget-usd 5.00 "query"`. `--max-turns`: "Limit the number of agentic turns (print mode only). No limit by default." Result behaviours at the cap (subtype / exit code) were truncated in my fetch [NOT FOUND]; check `result` JSON `subtype` empirically.
- Permission flags: `--allowedTools "Bash(git diff *),Read"` (prefix match, space before `*` matters); `--permission-mode dontAsk` ("useful for locked-down CI runs"); `--permission-prompts none` (v2.1.259+); from v2.1.302 `-p` starts in Manual mode when nothing sets a mode, and calls needing approval are denied. `--no-session-persistence` (print mode) avoids writing sessions. `--fallback-model`, `--strict-mcp-config --mcp-config`, `--settings`, `--exclude-dynamic-system-prompt-sections` (better cache reuse across machines).
- `--bare` is recommended for CI ("so Claude Code starts without loading the host's hooks, plugins, auto memory, or CLAUDE.md"), needs `ANTHROPIC_API_KEY`. It disables CLAUDE.md and skills discovery: for a framework whose value *is* CLAUDE.md/skills/hooks, a bare run is the no-framework arm; the framework arm must load them via `--plugin-dir`, `--append-system-prompt-file`, `--add-dir`, which do not run hooks.
- Output: `--output-format json` gives `result`, `session_id`, `total_cost_usd`, per-model cost and `usage`; `stream-json --verbose` last line is a `result` message. `system/init` lists `plugins`, `plugin_errors`, `mcp_servers`, `mcp_server_errors` - "a CI gate can fail on a non-empty array" (a plugin that silently failed to load would otherwise produce a bogus baseline-equals-treatment result).
- Exit: 0 on success, non-zero on failure; SIGTERM -> 143. Background work can keep `-p` open up to 10 min (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`).
- Piped stdin capped at 10 MB.

## PART 4: Token walls

Official [READ]:
- Usage-limit auto-continue (interactive-mode, v2.1.234+): "Claude Code waits in the open session and continues the task on its own after the limit resets. Automatic continue is on by default in interactive sessions signed in with a claude.ai subscription." At reset it "prompts Claude to pick the task up where it stopped. It doesn't resend your last message." Needs the session left open; permissions still prompt, "so the task can stop on a prompt while you're away." Cap: "After three automatic continuations, automatic continue stops" (`/rate-limit-options` to choose; count resets on a new prompt). Managed setting `autoContinueAtUsageLimit`. Cancel with Esc/Ctrl+C. Does not apply to `-p`/API-key runs as far as these docs say (feature is described for claude.ai interactive sessions).
- Switching models during the wait "continues right away if it is [available]" (costs docs: seat limits are shared across models; model-specific "Opus limit"/"Sonnet limit" messages can be dodged with `/model` to another family) - but a model switch forfeits the prompt cache (PreModelSwitch exposes `estimated_cache_write_usd`; docs example: 182k-token context, about $1.14 to re-cache on switch).
- Compaction cost (prompt-caching): the summarisation request "repeats your conversation's system prompt, tools, and the history being summarized"; warm cache -> "costs a fraction of what the context size suggests"; cold -> "there is no cache left to read, so the summarization request reprocesses that history as uncached input. This is why /compact costs the most when you resume an old session." Costs page: "`/compact` reads the conversation it summarizes, so compacting a large context is itself a large request. When you want a fresh start instead of continuity, `/clear` costs nothing."
- Cache TTL: main conversation 1h only on a subscription within plan usage; otherwise 5m (and once over plan usage and drawing on usage credits, drops to 5m). Subagents/compaction default 5m. Set via `CLAUDE_CODE_PROMPT_CACHE_TTL` / `promptCacheTtl` (v2.1.242+).
- Resume: "Claude Code sends the whole conversation again, and the request reads from the cache whatever part of its prefix is unchanged and still within the cache lifetime." SessionStart hook on resume/fork exposes `context_tokens`, `prompt_cache_likely_expired`, `estimated_cache_write_usd` (v2.1.251+) so a hook can warn or recommend a handoff instead of resume.
- Idle compaction: with a 1h TTL, Claude Code "can compact" an idle long conversation (setting `idleCompaction`, v2.1.290+ to turn off). Background token drains while idle: session recap, prompt suggestions (skipped near limit), `/loop` tasks, cross-session messages, goal check-ins (max 3 idle per goal).
- Official clear/compact advice: "Clear between tasks ... Use /rename before clearing so you can find the session later, then /resume"; "Add custom compaction instructions: `/compact Focus on code samples and API usage`"; a `# Compact instructions` section in CLAUDE.md is honoured; "Pick your model and effort level at the top of a session, then save /compact for natural breaks between tasks." `/rewind` truncates to an already-cached prefix (cheaper than compacting).
- Numbers in official docs: average ~$13/developer/active day, $150-250/month, <$30/day for 90% [READ]; agent teams about 7x tokens [READ]. No official number for handoff-file vs resume savings [NOT FOUND].

Practitioner [SEARCH-ONLY, not opened; anecdotal]:
- One post (bestagent.dev idle-resume cost) claims a handoff file cuts resume cost from the full history to "a few hundred tokens"; the 2026 Japanese-language log and others say `/compact` must read the whole conversation, so a fresh session with a handoff note is about the same one-time cost but cheaper afterwards; a heuristic of compacting at ~60% context; one post claims a fresh session can start with 50.6% of a 200k window consumed by overhead. No controlled comparison found. A bug report (claudeissues.com 81636) says `/clear` did not reset a "Context limit reached" state and a full process restart was needed (closed not planned) - treat as unverified.

Design implications:
1. Do not build your own "continue after reset" for interactive subscription sessions: it is built in (cap 3). A hook is useful only for `-p`/CI or for writing a checkpoint when StopFailure fires with `rate_limit`, with the mapping caveat above.
2. A checkpoint file written by PostCompact (`compact_summary`) / Stop / SessionEnd (1.5s budget; raise `timeout`) plus a SessionStart `source=clear|resume|compact` re-injector gives `/clear` + handoff cheaply; the cost of resume is a cold-cache re-read of the full context, which the SessionStart fields now quantify.
3. PreCompact stdout is the supported way to add "preserve these facts" instructions at no extra call.
