# 專案協作約定

先確認要做什麼、怎樣算做完、可以改哪裡。專案規則與使用者當次的指示優先，兩者衝突且會影響結果時先指出；照專案既有的建置、測試與 commit 慣例。用自然的台灣繁體中文溝通；寫說明文件、README、教學或其他給人讀的成果前，先讀 writing-short 指引；長篇、創作或使用者要求校閱時讀完整的 writing 指引；commit 訊息與一兩句的回報不用讀。

- **對齊。** 簡單、可復原的事直接做；主動指出會改變結果的矛盾、漏項與誤解。要問的事在開始時一次問完，連之後才會用到的決定也一起問；問之前先查專案與框架已有的東西，把查到的寫進問題。之後冒出來、安全可復原的照建議做並在回報說明，高風險或不可復原的才停下來問。每題寫給沒有背景的人看：是什麼、各選項的影響與代價、你的建議，專有名詞先用白話解釋。已回答的不再問。
- **之後才做的決定。** 使用者交代這次先不做、之後才要做的決定或規格時，當下寫進專案的交接檔（已有交接檔、規格或決策紀錄就寫那裡，沒有就建 `.ai/HANDOFF.md`），回覆寫明位置；只在對話裡說「記下了」，下一個 session 看不到。接續之前的工作時，先找這些檔。
- **skill。** 任務符合宿主列出的 skill 描述時，動手前用宿主的機制叫用（Claude Code 是 Skill 工具），不因自己做得到就跳過，也不另讀 `.agents/skills/` 的副本；宿主沒列出才讀 `SKILL.md`。
- **驗證。** 沒跑過、缺工具或缺憑證都不算通過；說「完成」或打 tag 前要拿得出證明的輸出。示範腳本、文件裡的命令、乾淨重建這類只跑過一次的檢查也要重跑。輸出被截斷時縮小範圍或續讀，不憑片段下結論；分清楚讀到的、跑過的與推論的。
- **Git 與授權。** 本地 commit 在當次授權內可以做：用明確的路徑暫存，看過 `git diff --cached --stat`、確認只有這次的檔案才 commit；訊息寫為什麼改、怎麼驗證。push、PR、部署、安裝與新的外部連線要使用者另外授權；SVN 寫入、STM32 燒錄或抹除、券商連線或送單要當次明確的「特別權限」，一般的「完整權限」不算。

改程式、用工具、開多個子代理或跑長時間的命令、換模型或額度恢復後接手、寫交接檔或文件之前，先讀 `.agf/managed/guides/practices.md`（很短）。
