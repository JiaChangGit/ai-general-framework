# 專案協作約定

先確認目前任務、成功條件與允許修改的範圍。遵循目標專案既有的建置、測試與貢獻慣例；本框架的範例不會自動成為專案要求。

開始任務時，用 `profile show --root <目標專案目錄>` 取得有效偏好，將語言、圖解與教學選擇用在這次成果；同一任務不必反覆讀取未變的設定。當次指示優先，權限仍以宿主與當次授權為準，JSON 範例不會自動變成生效政策。

- 簡單且可逆的工作直接處理。主動指出會改變結果的矛盾、漏項與誤解，只追問無法從現有材料確定的部分；已有答案時不要反覆要求確認。問題含專有名詞時，先用白話解釋意思與選項影響。提出做法或選項前，先查框架與專案已有的 skill、指引、`agf` 工具和評測，把查到的寫進問題。
- 追程式、除錯、審查差異、帶讀論文或規格、教學時，先看宿主列出的 skill：描述符合這次任務的，動手前就用宿主的機制叫用（例如 Claude Code 的 Skill 工具），不要因為自己也做得到就跳過；不另外讀 `.agents/skills/` 的副本。宿主沒有列出時，才讀 `SKILL.md`。先定位相關程式與日誌範圍再讀，避免一開始載入整份日誌；截斷時縮小或續讀。保留版本、來源位置與可重現步驟，分清楚實讀、實測和推論。
- 修改既有程式時先找可重用功能與最小修改；創作則依已定設定與作品目標發展。不要為了可能的未來需求增加抽象層、代理角色或依賴。
- 以符合變更風險的檢查驗證結果。缺工具、缺憑證、沒跑測試，都不算通過。
- 先用已有的 `agf` 工具：`run`（限時、限量執行並保存輸出）、`context`（有界的搜尋與摘錄）、`source`（PDF、網頁等來源的摘錄）、`files`（批次改名）、`binary`（二進位欄位）、`diagram`（圖源）、`git scope`（變更範圍）、`task`（落盤交接）、`check`（品質檢查）。
- 「畫個圖」「畫流程圖」「把這個視覺化」等技術圖解、二進位欄位和外部能力，做法都在 tools 指引：AI 只寫 Mermaid 圖源，不撰寫 SVG／圖片內容；不憑欄位名稱或硬體位址猜檔案 offset；需要外部能力時先找宿主已連接的工具，不因工具名、star 或省 token 宣傳自動啟用。
- 製作簡報、文件、網頁、圖片或影音成果時，先讀 writing 指引選按需參考；不編數字，不假稱分享成功。
- 當次任務授權可涵蓋範圍內改檔、測試與 Git 本地 commit。push、建立 PR、部署、安裝及新增外部連線依目前使用者另行授權。SVN 寫入 repository、STM32 燒錄或抹除、券商連線或送單，需要當次明確的「特別權限」；一般的「完整權限」不包含這些動作。
- 說明使用自然的台灣繁體中文；寫或改給人讀的說明前，先讀 writing 指引。配合讀者程度，把目的、因果和例子接起來；不編造 commit 當時的修改原因。

現有專案規則與目前使用者指示優先；衝突會影響任務時，先提出具體差異。工具模式和有效入口會由配置工具附在下方；不要自行切換執行環境。
