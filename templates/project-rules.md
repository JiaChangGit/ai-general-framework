# 專案協作約定

先確認這次要做什麼、怎樣算做完、可以改哪些地方。照目標專案既有的建置、測試與 commit 慣例；本框架的範例不會自動變成專案的規定。專案規則與使用者當次的指示優先，衝突會影響結果時先指出差異。

- **對齊。** 簡單、可復原的事直接做。主動指出會改變結果的矛盾、漏項與誤解；只問材料裡找不到答案的事，已回答的不再問。提出選項前先查框架與專案已有的 skill、指引、`agf` 工具和評測，把查到的寫進問題；專有名詞先用白話解釋，並說明每個選項會改變什麼。
- **skill。** 追程式、除錯、審查差異、讀論文或規格、教學時，先看宿主列出的 skill，描述符合就在動手前用宿主的機制叫用（Claude Code 是 Skill 工具），不因自己也做得到就跳過，也不另外讀 `.agents/skills/` 的副本；宿主沒列出時才讀 `SKILL.md`。
- **讀資料。** 先找出相關的程式與日誌範圍再讀；被截斷時縮小範圍或續讀。分清楚讀到的、跑過的與推論的。
- **改程式。** 依序問：需要改嗎？專案裡已經有嗎？標準函式庫或已安裝的套件有嗎？幾行改得完嗎？都不行才寫新的。不為可能的未來需求加抽象層、代理角色或相依套件。
- **驗證。** 檢查的強度配合改動的風險；缺工具、缺憑證、沒跑測試都不算通過。寫「完成」或打代表完成的 tag 前，要拿得出證明它的輸出。只做過一次的檢查（示範腳本、文件裡的命令、在乾淨環境重建）也要重跑，它們最容易在之後的改動裡悄悄壞掉。
- **工具。** 先用已有的 `agf` 工具：run、context、source、files、binary、diagram、git scope、task、check，用法見 tools 指引。技術圖只寫 Mermaid 圖源；不憑欄位名稱猜二進位檔的 offset；需要外部能力時先找宿主已連接的工具，不因名氣或省 token 的宣傳就啟用。
- **續接與用量。** 同時開多個子代理、執行長時間的命令，或用量可能不夠之前，先把進度、已做的決定和下一步寫進交接檔（workflow 指引的「續接」）；每完成一個里程碑就更新。使用者換模型或在額度用完後要你再試一次時，先讀那份交接檔。
- **Git 與授權。** 本地 commit 在當次授權內可以做：用明確的路徑暫存，看過 `git diff --cached --stat` 只有這次的檔案才 commit；訊息寫為什麼改、怎麼驗證，不編造當時的理由。push、建立 PR、部署、安裝與新增外部連線要使用者另外授權。SVN 寫入、STM32 燒錄或抹除、券商連線或送單需要當次明確的「特別權限」，一般的「完整權限」不包含這些。
- **寫給人讀的文字。** 用自然的台灣繁體中文；寫說明、文件或其他成果前先讀 writing 指引。配合讀者程度，把目的、因果和例子接起來；不編數字，不假稱已分享。需要語言、圖解或教學偏好時，用 `profile show --root <專案目錄>` 查。
