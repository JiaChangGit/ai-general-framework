# 行為案例怎麼使用

`scenarios.json` 是可重跑的任務與觀察條件。它不會用關鍵字替模型選 skill，也不會把輸出有某個標題當成功。

要驗收中文改寫，可另取 [writing-cases.json](writing-cases.json) 的 `request`、`facts`、`draft` 交給新對話，將 `preserve`、`observe`、`avoid` 留給審查者。先核對數字、否定、條件、責任人與未知是否保留，再評估是否好讀；清楚的原文可以保留。來源與限制見[寫作研究紀錄](../docs/writing-research.md)。

在指定 host／model／版本的新對話使用案例，提供它實際需要的原始檔案，並記錄這次安裝、可用的 skills。五個候選是 `trace-code`、`debug-root-cause`、`review-change`、`read-research`、`guide-learning`；新專案預設不安裝任何 skill。`expected_skill_if_available` 只表示該項確實可用時預期選用；`null` 表示這項任務不需要這五項。未安裝時，模型應依一般工作規則完成任務，不假稱載入不存在的 skill，也不因缺少它而自行安裝。選用正確名稱仍不代表成果合格。

案例中的程式、論文、規格、patch、log 或既有創作設定，須由測試者提供；缺少會影響結論的材料時應提出具體問題，不能補造。另用相同輸入、移除對應 skill 做一次對照，觀察是否仍能理解任務與遵守權限。普通產品討論、實作、創作及純文件擷取應保留一般工作流程。

保存實際工具軌跡、產物、耗時及能取得的 usage；核對結果、越界行為、必要互動與證據。研究任務則核對原始來源及推論範圍。比較改動前後時使用相同輸入與環境，讓審查者先看原始結果，再看作者的結論。特殊權限案例使用替身工具或唯讀紀錄觀察，不連接真實券商、寫入 SVN repository 或操作實體板子。

第一次在真實 host 驗證，可先做一組小對照：

1. 記錄 host、model、版本、作業系統、框架 commit、已配置及其他來源可用的 skills；用 `project status` 確認配置，再以宿主提供的清單或探索結果確認能發現技能。檔案存在與宿主能發現是兩項觀察。
2. 選一個與技能相符的真實任務，以及一個不應使用它的小任務，例如指定拼字修正。在各自的新對話提供相同權限與必要原始材料，先不點名技能，保存可取得的載入／呼叫紀錄、產物與結果。宿主沒有公開載入紀錄時，記為未知，不能從回答風格推定已載入。
3. 用相同規則、工具、模型設定與材料，在另一份不含該技能的隔離配置重做相符任務；確認全域或其他路徑沒有又提供同一技能，也不提供前次答案。這是在比較技能增益；若比較整套框架，則另做完全不配置框架的對照，兩者分開記錄。
4. 先核對成果正確性、證據、權限與不必要操作，再比較追問、返工、耗時及宿主實際提供的 usage。資料拿不到就留白；單次差異不能宣稱穩定改善，需要判斷效果時再重複並交錯執行順序。

先驗證主要使用的 host，再依實際需求重跑其他 host；某個模型通過不代表其他模型或版本通過。OpenCode 同 session 換模型可另外觀察上下文是否延續，但不強制產生交接檔。這份步驟是待執行方法，已跑過的環境與限制以驗證紀錄為準。

靜態 `audit`、腳本測試與真人教學成果是不同證據。本輪的獨立 forward-test 見 [驗證紀錄](../docs/verification.md)；只有少量樣本，不能據此宣稱通用觸發率、token 節省或真人已學會。
